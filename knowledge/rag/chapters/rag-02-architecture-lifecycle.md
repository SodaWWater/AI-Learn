# RAG 系统架构与生命周期

## 本章概要

一个可落地的 RAG 系统有两条主链路：

- **离线或准实时知识链路**把来源转化为带版本、权限和元数据的可检索索引；
- **在线问答链路**把用户问题转化为检索请求，经召回、过滤、融合和重排形成证据，再生成带引用或拒答状态的结果。

两条链路由文档版本、Chunk ID、索引版本和追踪 ID 连接，并由更新、评估与反馈形成闭环。生产级架构的关键不只是组件齐全，而是组件边界清楚、数据契约稳定、故障能够定位、任务能够幂等恢复、模型和索引能够独立灰度。

关系图见 [`RAG-02 系统架构与生命周期`](../../../learning/rag/maps/rag-02.md)。

## 1. 离线知识库构建全流程（RAG-02-001）

“离线”表示不阻塞普通用户问答，并不意味着只能定时全量运行。它可以由批任务、文件事件或持续摄取服务执行。

### 1.1 标准阶段

| 阶段 | 输入 | 核心处理 | 输出 |
|---|---|---|---|
| 来源发现 | 文件、网页、数据库记录、对象存储事件 | 枚举、权限校验、内容哈希、变更判断 | `SourceObject` |
| 获取与解析 | 原始对象 | 下载、解码、OCR、版面和结构恢复 | `ParsedDocument` |
| 清洗与治理 | 解析元素 | 去噪、去重、脱敏、ACL、时间字段 | 规范化文档 |
| 切分 | 文档结构 | Chunking、父子关联、上下文补充 | `Chunk[]` |
| 表示 | Chunk | 稠密 Embedding、稀疏特征、实体或图抽取 | 多种检索表示 |
| 写入与建索引 | 表示、正文、元数据 | Upsert、倒排/ANN/图索引构建 | 候选索引版本 |
| 质量门禁 | 样本、统计与 Golden Query | 解析抽检、召回回归、权限检查 | 验收报告 |
| 发布 | 已验收索引 | 预热、别名切换、灰度、旧版保留 | 在线可读版本 |

### 1.2 为什么要保留中间产物

如果只保存最终向量，解析器升级或 Chunk 策略变更时只能重新下载全部来源，也无法判断错误最早在哪一步发生。建议保存有版本的中间表示：

```text
source object -> parsed document -> normalized elements -> chunks
              -> dense/sparse/graph representations -> index release
```

每一层至少记录输入哈希、处理器版本、配置版本、输出位置、状态和时间。中间产物是否长期保存取决于成本、合规和可复现要求；敏感原文不能为了排障而无限留存。

### 1.3 发布而不是“写完即上线”

将写入索引与在线可见分开：数据先进入候选版本，完成数量、Schema、权限、抽样检索和回归评测后，再通过别名或路由切换发布。否则半完成索引、混合 Embedding 版本或权限元数据缺失会立即影响用户。

## 2. 在线问答全流程（RAG-02-002）

### 2.1 标准阶段

1. **请求接入**：认证、租户识别、限流、生成 `request_id` 和 `trace_id`。
2. **查询理解**：规范化、多轮问题独立化、意图识别、是否需要检索、知识源路由、过滤条件抽取。
3. **多路召回**：稠密、关键词、结构化、图或外部搜索并行返回候选。
4. **候选治理**：执行 ACL、时间有效性、来源可信度和内容安全过滤。
5. **融合与重排**：合并不同通道分数或名次，用 Reranker 提升精排相关性，去除重复和低价值证据。
6. **上下文构建**：按 Token 预算选择、压缩、排序和编号证据，添加来源元数据与输出约束。
7. **生成或抽取**：模型根据证据回答；证据不足时拒答或转人工/工具。
8. **生成后验证**：结构校验、引用映射、敏感信息检查、必要时做断言—证据核查。
9. **响应与观测**：返回答案、引用和必要状态，异步记录阶段指标和反馈入口。

### 2.2 在线状态不是一个字符串

推荐把在线数据分成至少三类对象：

```text
QueryRequest -> Candidate[] -> Evidence[] -> GenerationContext -> Answer
```

- `Candidate` 是某一召回通道返回的候选，允许高召回、分数不可直接跨通道比较；
- `Evidence` 是通过权限、质量、融合和重排后，允许进入生成上下文的证据；
- `Answer` 包含文本以外的引用、拒答状态、版本和追踪信息。

这种分层可以避免把“召回到”错误地等同于“模型看到”，也可以分别计算召回覆盖、重排增益和生成忠实度。

## 3. 召回、过滤、生成三段式链路（RAG-02-003）

三段式是用于排障和指标设计的逻辑划分，不一定对应三个独立服务。

### 3.1 召回阶段

目标是在可接受成本内尽量让正确证据进入候选集。典型参数是各通道 `top_k`、相似度阈值、过滤条件和查询变体数。主要看 Recall@K、Hit Rate、候选规模和延迟。

### 3.2 过滤与排序阶段

目标是从候选中保留有权限、有效、可信、相关且互补的证据。包括 ACL、时效、去重、融合、Rerank、多样性和来源控制。主要看 nDCG、MRR、正确证据保留率以及重排前后名次变化。

### 3.3 上下文与生成阶段

目标是把有限证据组织为模型可正确使用的上下文，并生成有依据、格式正确、可引用的结果。主要看 Faithfulness、Answer Correctness、Citation Accuracy、拒答质量和端到端任务成功率。

一个常见误区是用最终答案指标直接调 `top_k`：答案错误可能来自知识缺失、召回、排序、截断或模型未忠实使用。没有阶段性数据就无法知道该改哪里。

## 4. 离线组件的职责边界（RAG-02-004）

| 组件 | 应负责 | 不应偷偷负责 |
|---|---|---|
| Loader / Connector | 发现、读取来源，记录版本和访问状态 | 猜测复杂阅读顺序或直接生成答案 |
| Parser | 恢复文本、版面、表格、图片等元素 | 按任意固定长度切块并丢掉结构信息 |
| Normalizer / Governor | 清洗、去重、元数据、权限、合规 | 修改事实以迎合模型 |
| Splitter | 按结构和检索目标构造 Chunk、父子关系 | 选择在线 Top-K 或生成答案 |
| Embedder | 按固定模型和版本生成向量 | 将不同维度或归一化规则的向量混写 |
| Index Writer | 校验 Schema、幂等写入和索引构建 | 未经质量门禁就自动发布 |
| Retriever | 根据查询和过滤条件取得候选 | 把候选直接当最终可引用证据 |

边界的意义是可以单独替换和评测。例如 Parser 升级后只需重放其下游阶段；Embedding 模型升级不应改变稳定的 `document_id` 和 `chunk_id` 语义；Retriever 更换索引算法不应迫使 Generator 改输入协议。

## 5. Retriever、Reranker 与 Generator（RAG-02-005）

### 5.1 Retriever

Retriever 面对整个可检索语料，强调吞吐和候选覆盖。它可以是 BM25、向量 ANN、SQL、图查询或多通道路由器。输出必须保留通道名、原始分数、名次、索引版本和过滤信息。

### 5.2 Reranker

Reranker 只处理较小候选集，可以用更昂贵的 Query—Document 联合编码、LLM 打分或业务规则。它优化候选顺序和选择，不负责修复知识库中不存在的证据。若 Retriever 没召回正确内容，Reranker 无法凭空恢复。

### 5.3 Generator

Generator 消费已经选择并编号的证据，负责综合、抽取、解释或形成结构化输出。它必须知道：哪些文本是指令，哪些是数据；哪些证据可信；无证据时怎样拒答；引用怎样映射。Generator 的通用知识可用于解释，但在受证据约束的事实任务中不能把参数记忆伪装成来源事实。

### 5.4 三者的性能预算

典型在线延迟可以分解为：

$$
T_{total}=T_{route}+\max(T_{retrieve,1},\ldots,T_{retrieve,n})+T_{rerank}+T_{context}+T_{generate}+T_{post}
$$

并行召回时取最长通道而不是简单求和；生成往往占大头，但低效的串行查询、过大候选集和未批处理的 Rerank 也可能成为瓶颈。预算应按阶段设置超时和降级，而不是只设置一个总超时。

## 6. 数据流、控制流与错误流（RAG-02-006）

### 6.1 数据流

数据流是业务对象本身：原始文档、解析元素、Chunk、向量、查询、候选、证据、上下文和答案。每次变换都应保存输入/输出标识及版本。

### 6.2 控制流

控制流决定执行哪些步骤：任务编排、检索路由、并行或串行、超时、重试、停止条件、降级和人工审批。例如无需外部事实的闲聊可以绕过检索；复杂问题可以进入多步检索；高风险请求可以强制使用可信知识源。

### 6.3 错误流

错误流传递异常和低质量状态，至少区分：

- **技术错误**：网络失败、模型超时、索引不可用、Schema 不兼容；
- **数据错误**：解析空白、编码失败、权限字段缺失、向量维度错误；
- **质量错误**：零召回、低相关、冲突证据、引用不支持断言；
- **业务状态**：无权限、无答案、需要澄清、转人工。

不要把所有情况都变成 HTTP 500，也不要在错误时静默让模型无证据自由回答。错误类型决定可重试性、降级路径和用户提示。

## 7. 来源到答案的可追溯链路（RAG-02-007）

### 7.1 标识层级

```text
source_id
  └── document_id + document_version
        └── chunk_id + chunk_version
              └── representation_version
                    └── index_version
                          └── request_id / trace_id
                                └── citation_id / answer_id
```

- `document_id` 表示逻辑文档身份，`document_version` 表示某次内容状态；
- `chunk_id` 应能稳定定位切分结果，切分策略改变时要有版本或新 ID；
- `representation_version` 包括 Embedding 模型、维度、归一化和稀疏编码版本；
- `index_version` 表示一次可发布、可回滚的索引快照或逻辑版本；
- `trace_id` 把在线各阶段事件串起来；
- 引用记录最终使用了哪个 Chunk、来自哪个文档版本及答案中的支持范围。

### 7.2 引用不是只保存 URL

网页可能更新，文件名可能重复，数据库记录也可能被覆盖。可审计引用至少需要来源 ID、版本/时间、定位信息以及内容哈希；面向用户可以显示短链接和标题，后台仍要保留可复现定位。

### 7.3 删除传播

删除文档时要能够从 `document_id` 找到所有 Chunk、向量、倒排项、图节点、缓存、评估副本和引用索引。只从向量库删除但保留答案缓存或日志副本，不算完成删除合规。

## 8. 批处理、流式摄取与事件驱动更新（RAG-02-008）

| 模式 | 适合 | 优点 | 主要风险 |
|---|---|---|---|
| 定期批处理 | 大批量、允许小时级新鲜度 | 简单、吞吐高、易做全局去重 | 更新延迟、失败重跑范围大 |
| 流式摄取 | 持续高频记录、低延迟 | 新鲜度高、可持续处理 | 顺序、背压、重复和小批效率 |
| 事件驱动 | 文件新增/修改/删除可发事件 | 精确触发、便于增量 | 丢事件、乱序、事件与真实状态不一致 |
| 混合模式 | 大多数生产知识库 | 事件增量 + 周期对账 | 架构更复杂但更稳健 |

事件是“可能发生变化”的通知，不应被当作最终事实。消费者仍需读取来源当前状态、比较内容哈希和版本。周期性全量对账用于发现丢失事件、权限变化和长期漂移。

## 9. 模块化接口与组件可替换性（RAG-02-009）

### 9.1 稳定协议优先于框架对象

不要让下游直接依赖某个框架私有的 `Document` 类。先定义自己的最小领域 Schema，再在适配器中转换：

```text
Retriever.search(QueryRequest) -> Candidate[]
Reranker.rank(QueryRequest, Candidate[]) -> Evidence[]
ContextBuilder.build(QueryRequest, Evidence[], Budget) -> GenerationContext
Generator.generate(GenerationContext) -> AnswerDraft
Verifier.verify(AnswerDraft, Evidence[]) -> Answer
```

每个接口需要明确：字段语义、是否可空、分数方向、版本、超时、错误类型、最大批量和幂等性。否则“可插拔”只停留在类名层面。

### 9.2 双轨替换

替换 Embedding、Retriever、Reranker 或 Generator 时，先影子运行或离线回放，再灰度一小部分流量。新旧版本同时写入统一评测日志，比较质量、延迟、成本和失败分布。不能只凭几个手工问题宣布升级成功。

### 9.3 防止组合爆炸

模块化不代表所有组件任意组合。向量维度和相似度、查询/文档前缀、Chunk 格式、Reranker 最大长度、生成模型上下文和 Prompt 模板存在兼容约束。应为经过验证的组合定义 `pipeline_profile`，而不是把每个参数直接暴露给线上调用方。

## 10. 任务状态、幂等与失败恢复（RAG-02-010）

### 10.1 任务状态模型

摄取任务可使用明确状态，而不是只有“成功/失败”：

```text
DISCOVERED -> FETCHED -> PARSED -> NORMALIZED -> CHUNKED
           -> EMBEDDED -> INDEXED -> VALIDATED -> PUBLISHED
```

每个状态保存完成时间、处理器版本、输入输出引用、尝试次数和最后错误。`PUBLISHED` 是索引版本级状态，不应由单个文档任务直接设置。

### 10.2 幂等键

重复执行不能制造重复 Chunk 或脏向量。常见幂等键可由以下内容构成：

```text
(tenant_id, source_id, document_id, document_version,
 processor_name, processor_version, config_hash)
```

Upsert 前比较内容哈希；消息确认在持久化状态之后；外部调用返回不确定时，用幂等键查询结果，而不是盲目重复扣费或写入。

### 10.3 重试与死信

- 短暂网络失败可指数退避重试并加入抖动；
- 无权限、文件损坏、Schema 不兼容等永久错误不应无限重试；
- 达到次数上限后进入死信队列或待人工处理状态；
- 重试从最近一个已验证的阶段继续，而不是总从下载源文件开始；
- 发布前检查整个索引版本的完整性，部分失败不得伪装成全量成功。

### 10.4 恢复与回滚

索引发布使用不可变版本与可切换别名。发现质量回归时，将在线读路由切回上一个已验证版本；新版本继续保留供排障。恢复能力必须定期演练，包括对象存储、中间产物、向量/倒排/图索引以及配置和模型版本。

## 11. 工程实现参考

### 11.1 推荐的服务边界

小规模项目可以同进程实现，但逻辑上仍保留边界：

```text
Ingestion API / Scheduler
  -> Workflow + State Store
  -> Parser workers
  -> Chunk / Representation workers
  -> Index writer + Release manager

Query API
  -> Auth / Policy
  -> Query orchestrator
  -> Retrieval adapters
  -> Reranker
  -> Context builder
  -> Generator / Verifier
  -> Trace + Feedback
```

只有在吞吐、资源、隔离或团队边界确有需要时才拆成独立网络服务。过早微服务化会增加序列化、调用链和版本协调成本。

### 11.2 配置与版本

一次可复现实验至少固定：

- 来源快照或时间范围；
- Parser、OCR、清洗和 Chunk 配置；
- Embedding 模型、维度、前缀和归一化；
- 索引类型及参数；
- Query 改写、召回通道、Top-K、融合和 Rerank；
- Prompt、上下文预算、生成模型及采样参数；
- 评测集版本和指标实现。

建议把这些汇总为不可变 `pipeline_version`，并让每个在线响应记录实际生效版本。

### 11.3 可观测性

| 层级 | 必看信号 |
|---|---|
| 摄取 | 待处理数、阶段成功率、解析空白率、Chunk 数分布、更新延迟 |
| 索引 | 文档/Chunk 数、版本、构建耗时、失败写入、删除滞留 |
| 检索 | 各通道延迟、候选数、过滤率、零召回、缓存命中 |
| 重排 | 批量大小、耗时、正确证据名次变化、截断率 |
| 生成 | 首 Token/总延迟、输入输出 Token、拒答、结构错误 |
| 端到端 | 任务成功、答案质量、引用、成本、用户反馈和错误归因 |

## 12. 常见失败与排障顺序

### 12.1 有答案但完全不相关

先确认是否使用了正确租户、知识源和索引版本；再看 Query 改写是否漂移、召回候选、过滤和重排；最后才调 Prompt。若正确证据从未进入上下文，修改生成提示通常无效。

### 12.2 新文档查不到

沿状态链检查：事件是否到达、内容哈希是否被误判未变、解析是否成功、Chunk 是否生成、Embedding 是否匹配当前索引、写入是否完成、索引版本是否发布、在线服务是否仍缓存旧版本。

### 12.3 重复数据和答案冲突

检查幂等键、逻辑文档 ID 与版本、删除旧 Chunk 的传播、近重复检测和有效时间。不能简单在生成提示里要求“选择最新”，因为检索和引用层仍可能返回旧记录。

### 12.4 故障时模型仍自信回答

检查错误流是否被吞掉、Retriever 超时后是否错误地传入空证据、Generator 是否能识别 `NO_EVIDENCE` 状态、降级策略是否允许参数知识回答，以及响应是否清楚标记降级。

## 13. 相似与易混概念

| 概念 | 容易混淆点 | 区别 |
|---|---|---|
| 离线建库 vs 在线检索 | 都会访问索引 | 前者构建并发布可读版本，后者只消费已发布版本 |
| Retriever vs 向量数据库 | 都返回近邻 | Retriever 是检索策略接口，向量库只是可能的执行后端 |
| Retriever vs Reranker | 都计算相关性 | Retriever 面向全库求覆盖和速度，Reranker 面向小候选集求精度 |
| 候选 Candidate vs 证据 Evidence | 都包含文本 | Candidate 尚未通过全部权限、质量和排序门禁 |
| 文档版本 vs 索引版本 | 都与更新有关 | 一个描述单文档内容，一个描述可整体发布/回滚的检索快照 |
| 失败重试 vs 质量恢复 | 都可能重新执行 | 技术失败可重试；低相关等质量问题需改数据或策略 |
