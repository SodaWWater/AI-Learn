# RAG 基础、价值与能力边界

## 本章概要

RAG（Retrieval-Augmented Generation，检索增强生成）在回答生成之前，从模型参数之外的知识源中检索与当前任务相关的证据，再让生成模型基于问题与证据完成回答。它把两种能力组合起来：

- **参数化能力**：模型参数中学到的语言、推理、模式和部分事实知识；
- **非参数化知识**：存放在文档库、数据库、搜索引擎、知识图谱或其他工具中的可更新信息。

RAG 的核心价值不是“接了一个向量数据库”，而是建立一条从外部知识到答案的、可更新且可追踪的证据通道。它特别适合知识经常变化、知识不在模型训练集、需要私域权限控制、答案必须给出处的任务；它不能天然保证事实正确，也不应成为所有 LLM 应用的默认架构。

关系图见 [`RAG-01 基础与边界`](../../../learning/rag/maps/rag-01.md)。

## 1. 定义、组成与工作目标（RAG-01-001）

### 1.1 研究语境与工程语境

Lewis 等人在 2020 年的 RAG 工作中，把预训练的序列到序列生成模型视为参数化记忆，把可由神经检索器访问的 Wikipedia 稠密向量索引视为非参数化记忆，并对检索到的潜在文档进行边缘化。给定输入 $x$、检索文档 $z$ 和输出 $y$，其一般形式可以写成：

$$
p(y\mid x)=\sum_{z\in\operatorname{TopK}(x)}p_{\eta}(z\mid x)\,p_{\theta}(y\mid x,z)
$$

其中 $p_{\eta}(z\mid x)$ 是检索器对文档的相关性分布，$p_{\theta}(y\mid x,z)$ 是生成器在输入和证据条件下生成答案的概率。

现代工程中“RAG”通常使用更宽的定义：检索器和生成器不一定联合训练，也不一定显式计算上述边缘概率；只要系统在推理时选择外部证据并让生成受到这些证据约束，通常就被归入 RAG。学习时应区分：

- **狭义 RAG 模型**：论文中的特定模型结构与训练目标；
- **广义 RAG 系统**：解析、索引、查询理解、检索、重排、上下文构建、生成、引用、评估和治理组成的工程系统。

### 1.2 最小组成

一个最小 RAG 闭环至少包含：

1. 可访问的知识源；
2. 把知识变为可检索单元的处理流程；
3. 根据查询取得候选证据的检索器；
4. 把问题与证据组装为模型输入的上下文构建器；
5. 根据证据生成或抽取结果的模型；
6. 把答案回链到来源的标识。

生产系统通常还需要查询改写、多路召回、权限过滤、重排、拒答、缓存、追踪、评测和索引版本管理。这些不是 RAG 定义的必要条件，却是系统质量可控的必要条件。

### 1.3 工作目标

RAG 同时优化四个目标，不能只看最终文字是否流畅：

| 目标 | 含义 | 典型验证 |
|---|---|---|
| 可获得性 | 需要的事实能从外部知识中找到 | Recall@K、Hit Rate、证据覆盖率 |
| 可利用性 | 检索到的证据能被模型正确使用 | Faithfulness、答案正确性、证据消融 |
| 可更新性 | 修改外部知识后能按约定生效 | 新鲜度、索引发布时间、更新延迟 |
| 可追溯性 | 答案能回到具体来源与版本 | 引用准确率、引用完整率、Trace |

## 2. 为什么需要外部知识通道（RAG-01-002）

### 2.1 知识截止

模型训练只覆盖训练数据中出现的信息，且训练、对齐、评估和部署之间存在时间差。模型上线后发生的政策、价格、库存、组织文档或研究进展不会自动进入参数。

### 2.2 知识空白

企业手册、内部工单、个人笔记、受权限保护的合同等私域数据通常没有进入通用模型训练集。即使模型具备相关领域的语言能力，也不能据此推断它知道某份私有文档的具体内容。

### 2.3 更新与纠错

参数知识的定向修改较困难：训练成本高、影响面难隔离，也不容易证明旧事实已完全删除。非参数知识可以按文档或记录更新、撤回、设定有效期并重新索引，因此更适合高频变化和可撤销知识。

需要注意，外部知识“可更新”不等于答案自动新鲜。变更检测、重新解析、重新向量化、索引发布、缓存失效和在线路由任何一步延迟，都会让旧信息继续被返回。

## 3. 私域知识、权限与审计（RAG-01-003）

RAG 可以让模型在不把全部私域内容写入参数的情况下访问知识，但安全边界必须贯穿整个检索链路：

- 摄取时记录租户、文档所有者、ACL、敏感等级、有效期和删除状态；
- 检索前从已验证的用户身份生成不可越权的过滤条件；
- 检索后再次验证证据权限，不能只依赖提示词要求模型“不要泄露”；
- 答案保存 `source_id`、`document_id`、`chunk_id`、文档版本和索引版本；
- 日志和评估样本也要脱敏，避免观测系统成为新的泄露通道。

“数据不进入模型参数”也不代表零泄露：数据仍会经过解析服务、Embedding 服务、向量库、模型 API、缓存和日志。选择托管或自部署组件时，必须核对传输、留存、训练使用政策和删除能力。

## 4. RAG 如何缓解幻觉，以及为什么不能消灭幻觉（RAG-01-004）

### 4.1 能缓解什么

RAG 给模型提供任务相关证据，减少仅凭参数记忆补全事实的必要；引用和证据展示使用户能够核查；拒答策略可以在证据不足时阻止无根据回答。

### 4.2 新增了哪些故障点

端到端成功依赖多个条件同时成立：

$$
P(\text{正确且有依据}) \approx
P(\text{知识存在})
\times P(\text{解析正确})
\times P(\text{召回相关})
\times P(\text{排序保留})
\times P(\text{模型忠实使用})
$$

这不是用来计算真实概率的独立性模型，而是用于故障归因的思考框架。典型失败包括：

- 知识库根本没有答案，或文档已经过期；
- OCR、表格解析、切分破坏了关键语义；
- Query 与文档表达不一致导致漏召回；
- Top-K 中有正确证据，但被重排器降权或被上下文预算截断；
- 文档包含冲突、恶意指令或不可信内容；
- 模型忽略证据、混合多个来源或生成证据没有支持的细节；
- 引用指向相关文档，却没有直接支持具体断言。

因此“用了 RAG”不能作为事实性保证。正确的工程结论是：RAG让事实性更可干预、更可观测，但仍需分层评估、拒答、引用验证、来源治理和生成后核查。

## 5. RAG 与相邻方案的区别、组合和选型

### 5.1 RAG 与微调（RAG-01-005）

| 维度 | RAG | 微调 |
|---|---|---|
| 主要改变 | 推理时输入和外部知识访问 | 模型参数、行为或任务能力 |
| 更新粒度 | 文档、记录、Chunk 或索引版本 | 训练数据集和模型版本 |
| 适合问题 | 最新/私域事实、来源引用、可撤销知识 | 风格、格式、领域行为、稳定任务模式 |
| 可追溯性 | 可保存证据与来源版本 | 参数内知识难回链到单条训练样本 |
| 运行成本 | 增加检索、重排和上下文 Token | 可能降低提示长度，但增加训练与模型管理成本 |
| 主要风险 | 漏召回、噪声、索引陈旧、注入攻击 | 遗忘、过拟合、知识更新困难、训练数据污染 |

“微调解决怎么说，RAG 解决说什么”是便于入门的近似，不是严格边界。微调也能改变事实输出，RAG 也会通过证据组织改变回答风格和推理路径。更准确的选型方法是先确定目标变量：要修改行为能力，优先提示/微调；要提供可变且可追溯的知识，优先外部上下文/RAG；两者可组合。

### 5.2 RAG 与长上下文（RAG-01-006）

长上下文是模型一次可接收更多 Token 的能力；RAG 是在大量候选知识中选择少量相关证据的机制。它们不是互斥方案：

- 文档少、总长度可控、需要跨全文整体理解时，可直接使用长上下文；
- 语料很大、频繁变化、需要权限过滤或引用时，RAG 更有结构优势；
- 可先检索文档级候选，再把少量完整文档放入长上下文；
- 可以根据查询类型、语料长度和成本动态路由。

LaRA 的公开基准结论是：RAG 与长上下文不存在跨模型、跨任务的统一赢家，结果取决于模型规模和长文本能力、上下文长度、任务类型以及被检索 Chunk 的特征。工程上必须在自己的数据集上比较，不能只依据上下文窗口标称长度。

### 5.3 RAG 与传统搜索（RAG-01-007）

传统搜索以返回文档、页面或排序列表为主要产物；RAG 以生成受证据支持的答案为主要产物。两者共享大量检索基础：倒排索引、BM25、稠密向量、过滤、排序、相关性评估和日志分析。

RAG 并不等于向量检索。关键词检索擅长精确术语、编号和罕见实体；稠密检索擅长语义近似；混合检索常比单一路径更稳。生成层还会带来断言级引用、证据冲突和模型忠实度等传统搜索没有直接承担的问题。

### 5.4 RAG 与模型记忆、上下文工程（RAG-01-008）

模型参数可视为长期但难精确修改的参数化记忆；当前对话和工作区状态属于短期上下文；外部知识库、用户画像、事件记录等可以构成可读写的长期非参数记忆。RAG 是“从外部记忆读取相关内容”的一种实现，不覆盖记忆写入、遗忘、合并、冲突处理和生命周期管理的全部问题。

上下文工程关注模型在每一步究竟看到什么，包括系统指令、工具结果、会话摘要、检索证据、状态和输出约束。RAG 是上下文工程的一部分；检索结果如果未经筛选、排序、压缩和标注，即使召回正确也可能形成糟糕的上下文。

## 6. 适合与不适合使用 RAG 的条件

### 6.1 高适配任务（RAG-01-009）

以下条件越多，RAG 的预期价值越高：

- 答案依赖模型训练后或频繁更新的信息；
- 事实来自企业、团队或个人私域资料；
- 需要给出来源、文档版本或审计记录；
- 不同用户只能访问知识库的不同子集；
- 知识可以形成可定位的文本、结构化记录、图节点或多模态元素；
- 用户问题与知识证据之间存在可学习或可设计的检索关系；
- 错误答案成本较高，需要拒答与人工复核入口。

典型任务包括内部制度问答、客服知识辅助、技术文档检索、法律或合规资料辅助、研究资料归纳以及带来源的分析助手。

### 6.2 收益有限或不适合（RAG-01-010）

- 任务主要考察创意、闲聊或稳定的通用能力，不依赖外部事实；
- 数据没有可靠证据，或答案只能来自隐含经验而非可检索内容；
- 语料极少且能稳定放入提示，检索层只增加复杂度；
- 要求极低延迟，而任何额外网络检索都不可接受；
- 需要对模型行为、格式或技能做稳定改变，问题本质不是知识缺失；
- 知识涉及无法满足的授权、隐私或数据驻留限制；
- 问题要求对全体材料做精确全局计算，而 Top-K 检索会系统性丢失长尾信息；
- 业务无法建立最小评测集，也无法观察检索证据与错误来源。

“不适合纯 RAG”不等于不能使用检索。可改用结构化查询、规则引擎、直接长上下文、数据库计算、微调，或将这些方法与 RAG 组合。

## 7. 工程落地：先建立可验证的最小边界

### 7.1 输入输出契约

最小系统不要只传字符串。建议至少保留以下对象：

```text
QueryRequest
  request_id, tenant_id, user_id, query, conversation_context,
  filters, locale, current_time

Evidence
  chunk_id, document_id, source_id, document_version, index_version,
  text_or_payload, retrieval_score, rerank_score, acl, valid_time

Answer
  request_id, text, citations[], confidence_or_abstention,
  model_version, prompt_version, index_version, trace_id
```

这些字段把“能回答”变为“能排障”：错误答案出现时，可以复现当时的查询、索引、证据排序、提示和模型版本。

### 7.2 第一版不应省略的可观测点

- 请求是否决定检索，使用了哪个知识源和索引版本；
- 各检索通道的候选 ID、分数、过滤原因和耗时；
- 重排前后名次变化；
- 最终进入模型的证据内容、顺序和 Token 数；
- 生成模型、提示版本、引用映射和拒答原因；
- 端到端延迟、Token 成本、缓存命中和错误码。

日志不能无条件保存完整敏感文本。可按权限保存哈希、ID、脱敏片段或受控采样，并设置留存和删除策略。

### 7.3 最小评测闭环

1. 从真实任务中选取有代表性的问题；
2. 标注可接受答案及其直接证据，而不只标最终答案；
3. 分别测知识覆盖、解析、检索、重排、生成忠实和引用；
4. 保存错误样本和首次失败阶段；
5. 每次调整 Chunk、Embedding、Top-K、Reranker 或 Prompt 后跑回归；
6. 只有端到端收益超过延迟、成本和维护代价时，才扩大使用范围。

## 8. 常见混淆与错误结论

| 错误结论 | 问题 | 正确理解 |
|---|---|---|
| RAG 就是向量数据库 | 把一个存储/索引组件当成完整系统 | RAG 可以使用稀疏、稠密、图、SQL 或混合检索 |
| 接入 RAG 就不会幻觉 | 忽略检索和生成的新故障 | RAG 只提高可控制性，仍需证据评估与拒答 |
| 上下文越长越不需要检索 | 忽略成本、权限、噪声和信息位置 | 应按任务和语料做 RAG/长上下文/混合路由实验 |
| 微调能把全部企业知识记住 | 忽略更新、删除和追溯 | 微调更适合能力与行为，外部知识更适合可变事实 |
| 相似度高就是证据正确 | 相关不等于蕴含 | 需要重排、来源控制和断言级证据验证 |
