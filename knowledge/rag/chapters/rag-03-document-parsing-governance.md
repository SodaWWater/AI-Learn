# 文档解析与数据治理

## 本章概要

文档解析的目标不是“尽可能多地抽出字符”，而是把异构来源恢复为可追踪、可检索、可重新组合的结构化元素，同时保留标题层级、阅读顺序、表格关系、图片说明、页码、权限和版本。数据治理进一步决定哪些内容允许入库、怎样去重、何时过期以及怎样删除。

解析错误具有上游放大效应：多栏顺序错乱会产生语义混杂的 Chunk；表头丢失会让单元格失去含义；页眉重复会占据召回；权限字段缺失可能造成越权。Embedding、Reranker 和 Prompt 很难可靠修复这些问题，所以解析质量必须在入库前独立评估。

关系图见 [`RAG-03 文档解析与数据治理`](../../../learning/rag/maps/rag-03.md)。

## 1. 统一文档模型与来源路由（RAG-03-001）

不同解析器输出格式各异。下游不应直接依赖工具私有对象，而应转换为自己的中间 Schema：

```text
ParsedDocument
  document_id, document_version, source_id, mime_type, language,
  title, created_at, effective_from, effective_to, acl,
  parser_name, parser_version, content_hash, elements[]

DocumentElement
  element_id, type, text, page, bbox, reading_order,
  heading_path, parent_element_id, caption_id,
  table_structure, media_ref, confidence, provenance
```

`type` 可以是 `heading`、`paragraph`、`list`、`table`、`image`、`caption`、`formula`、`code`、`header`、`footer` 等。`bbox` 与 `page` 让答案可以回到原页面，也让多模态元素重新关联；`confidence` 允许低置信区域走回退路径。

| 来源 | 首要保真目标 | 常见风险 |
|---|---|---|
| PDF | 视觉版面、页码、阅读顺序 | 文本顺序不等于视觉顺序，字体编码异常 |
| Word | 标题样式、列表、表格、批注 | 样式被滥用，浮动对象顺序不稳定 |
| HTML | 主体、标题层级、链接、表格 | 导航、广告、脚本和隐藏内容噪声 |
| Markdown | 标题、代码块、表格、链接 | 方言差异、嵌套 HTML、引用边界 |
| PPT | 幻灯片元素位置、备注、图表关系 | 纯文本抽取破坏空间关系 |
| 扫描图像 | OCR 文本、区域、置信度 | 倾斜、模糊、手写、复杂背景 |
| 数据库/API | 字段语义、主键、时间和权限 | 把结构化数据粗暴拼成无 Schema 文本 |

入口先做文件签名/MIME 检测、大小和加密状态检查，而不是只信扩展名。根据格式、是否存在文本层、页数、语言、版面复杂度和业务优先级选择解析路线。无法处理、受密码保护或超过限制的文件必须进入明确错误状态。

## 2. 文本型 PDF（RAG-03-002）

PDF 描述页面上字形的位置，不天然保存“段落”语义。即使能复制文字，也可能出现字符绘制顺序与阅读顺序不同、多栏交叉、连字符断词、自定义字体乱码、表格散成按坐标分布的词，以及页眉水印混入正文。

工程上应同时保留文本、词/行坐标、字体和页码，再通过版面模型或规则合并为块。对关键资料抽取后要做字符覆盖率、空页率、乱码率、阅读顺序和人工抽样检查，不能以“解析器没有抛异常”作为成功。

## 3. 扫描文档与 OCR（RAG-03-003）

OCR Pipeline 通常包含：页面渲染、旋转与方向检测、去倾斜和去噪、文本区域检测、文字识别、坐标回映射、行段重建及置信度保存。

分辨率太低会丢细节，过高会增加显存、延迟和存储；中英混排、公式、印章、手写体和低质量复印件需要专项模型或人工回退。OCR 后的拼写纠错不能无条件覆盖原识别结果，否则可能把编号、姓名和法律条款“纠正”为错误内容。建议保存原图引用、原始 OCR、规范化文本和变更记录。

## 4. 版面分析与阅读顺序（RAG-03-004）

版面分析先检测标题、正文、列表、表格、图片、Caption、页眉页脚等区域，再根据坐标、栏结构、字体和跨页关系恢复阅读顺序。复杂页面不能简单按 `y` 再按 `x` 排序：两栏页面会把左右栏同行内容交错；侧边栏、脚注和浮动图片也可能插入正文。

可将页面表示为有向图：元素是节点，“下一阅读元素”“Caption 属于图片”“脚注引用正文”等是边。最终线性文本只是其中一种投影，原始图结构应保留给专项 Chunking 和多模态检索。

## 5. 页眉、页脚、脚注和目录（RAG-03-005）

重复页眉页脚会在大量 Chunk 中反复出现，导致它们在 BM25 和向量检索中被过度召回。可按跨页位置、文本相似度、重复频率和字体样式识别，但不能粗暴删除所有页首/页尾内容：章节标题、页码、发布日期和保密等级可能是有效元数据。

脚注应保留与引用位置的关系；目录可以用于恢复层级，但通常不应与正文一样进入普通语义检索。推荐将噪声处理结果记录为元素类型和处理动作，而不是直接丢弃且无法审计。

## 6. 表格结构、序列化与结构化检索（RAG-03-006）

表格意义来自行列关系。只按阅读顺序拼接单元格会丢失表头、合并单元格和单位。建议保存表格标题、页码、上下文、行列坐标、`rowspan/colspan`、多级表头、单位、脚注、跨页连续关系和原页面定位。

常见索引形态可以并存：

1. Markdown/HTML 序列化，适合把小表放入生成上下文；
2. “表头 + 当前行”文本，适合行级语义召回；
3. 结构化表或 SQL，适合精确过滤、聚合和数值计算；
4. 表格图片或视觉 Embedding，适合复杂视觉表格。

大表不应整体塞入一个 Chunk，也不能依赖 LLM 对大量数字做精确聚合；优先使用结构化查询，将计算结果和原始行作为证据返回。

## 7. 图片、图表、流程图和 Caption（RAG-03-007）

处理视觉元素时至少保留图片本体、页面坐标、附近 Caption、所属章节和引用它的正文。可根据任务增加 OCR、视觉描述、对象/图表解析或视觉 Embedding。

机器生成 Caption 是派生信息，不应替代原图，也不能默认视为事实。图表数值如需精确回答，应使用图表数据提取或原始数据源；视觉描述更适合召回和概要。图像与文字必须共享 `document_id`、页面和关联 ID，避免检索到图片描述却无法展示原图或核查出处。

## 8. 公式、代码和特殊内容（RAG-03-008）

- 公式同时保存可读文本、LaTeX/MathML（若能恢复）和页面位置；上下标和矩阵结构不能只靠普通 OCR。
- 代码保留语言、缩进、代码块边界、文件/类/函数路径和注释；自然语言清洗规则不能直接施加到代码。
- 配置、日志、JSON/XML 等保留键层级和换行；必要时按记录而非固定字符切分。
- 电子签名、批注、修订痕迹是否纳入取决于业务语义和合规政策，必须显式配置。

## 9. 清洗、编码与格式标准化（RAG-03-009）

清洗只做有明确目标且可逆或可追踪的变换：Unicode 规范化、非法控制字符处理、换行/空白归一、断词修复、HTML 实体解码、明显乱码检测。不要无条件小写化、去标点、删除停用词或简繁转换，因为现代 Embedding、关键词匹配、引用定位和代码检索可能需要原始形式。

建议同时保存 `raw_text`、`normalized_text` 或至少保存变换日志与内容哈希。清洗后的字符偏移若用于高亮引用，需要建立到原始元素的映射。

## 10. 文档、段落与近似重复（RAG-03-010）

去重至少分三层：精确重复用规范化内容哈希；近似重复可用 SimHash、MinHash/LSH、n-gram 或 Embedding；同一逻辑文档的修订版则属于版本关系，不能误当无关重复。

还要区分“同内容不同权限/来源”。两份文本相同但 ACL 不同，不能简单合并为一个公开 Chunk；可以共享内容存储，但权限和来源映射必须是多值且在线取交集。近重复阈值应在业务样本上校准，模板相似不代表事实相同。

## 11. 元数据、来源和时间字段（RAG-03-011）

最低限度的元数据包括：

```text
tenant_id, source_id, document_id, document_version, chunk_id,
title, heading_path, page_or_locator, language, mime_type,
created_at, updated_at, effective_from, effective_to, ingested_at,
author_or_owner, acl, sensitivity, content_hash, parser_version
```

必须区分文档业务时间和系统摄取时间。`updated_at` 不能自动代表内容当前有效；政策可能提前发布但未来生效，也可能被新版本废止。元数据支持过滤、新鲜度排序、冲突处理和答案说明。

元数据不是越多越好：字段必须有明确语义、来源和更新责任。高基数字段会影响向量库过滤与索引性能，缺失值和枚举变化也需治理。

## 12. 权限、PII 与合规门禁（RAG-03-012）

入库前执行来源授权确认、恶意文件扫描、PII/密级识别、数据驻留与保留策略、ACL 继承和可删除性检查。权限既要附在逻辑文档上，也要能在 Chunk 和派生表示上执行；摘要、Caption、Embedding 和缓存同样属于派生数据。

PII 脱敏需区分永久删除、可逆令牌化和仅在展示层遮蔽。若问答任务合法需要特定字段，永久删除会破坏业务；若没有合法用途，则不应因为“Embedding 看不懂原文”而保留敏感内容。治理策略由业务与法律要求决定，不能只由模型效果驱动。

## 13. 解析工具与 Pipeline 选型（RAG-03-013）

不要只用一个“支持 PDF”复选框选工具。建立代表性文档集，按格式覆盖、版面能力、OCR/多语言、输出结构、批量和隔离能力、每页延迟、失败率、人工修复率、许可证和价格测试。

生产 Pipeline 可以采用快速默认解析器 + 复杂度检测 + 高质量回退解析器，而不是所有文档都走最贵路线。解析器升级必须固定版本并做回归，不能让同一索引中混入不可解释的不同输出格式。

## 14. 解析质量抽检与回退（RAG-03-014）

### 自动指标

- 成功页数、空页率、字符覆盖率、乱码/替换字符率；
- OCR 平均与低分位置信度，必要时使用 CER/WER；
- 标题、段落、表格、图片元素数量分布；
- 阅读顺序、表格结构和 Caption 关联的标注集准确率；
- 解析后 Chunk 数、长度和重复率异常；
- 从解析结果检索 Golden Evidence 的 Recall@K。

单纯字符相似度不能衡量结构正确性；最终还要用下游检索任务验证。抽检应按来源、格式、语言、页数、扫描质量、版面复杂度和敏感等级分层，而不是只随机看几个简单文件。

局部页面失败时可重渲染、更换 OCR/版面模型、人工复核或隔离该页；整个文档不可用时标记不可检索并通知责任方。禁止把空文本或低置信乱码正常入库。

## 15. 多模态元素关联与阅读顺序（RAG-03-015）

多模态文档不是“文本索引 + 图片索引”两条互不相干的列表。应建立元素图：

```text
heading -> paragraph -> figure reference -> image -> caption
                        -> table -> footnote
```

Chunking 时可沿这些关系选择上下文：检索到 Caption 时回取图片，命中表格行时带上表头，命中正文中的“如下图”时带上对应视觉元素。在线答案的引用可以定位到页面区域，而不是只返回整份 PDF。

视觉与文本模型的表示空间、分数分布和成本不同，多模态召回需要通道路由、分数融合和专项评测；将 OCR 文本当作图片全部语义会遗漏图形关系，将视觉描述当作精确数值又会放大错误。

## 16. 常见失败与排障

| 表现 | 首查位置 | 常见根因 |
|---|---|---|
| 句子前后错乱 | 阅读顺序和坐标 | 多栏按简单坐标排序 |
| 表格答案缺单位 | 表头/脚注关联 | 只保存当前单元格或当前行 |
| 总召回页眉 | 重复元素统计 | 页眉页脚未识别或被拼入每个 Chunk |
| 新版与旧版同时出现 | 文档身份与有效时间 | 把版本当成独立文档且未失效旧版 |
| 图片问题无法回答 | Caption/图片/正文关联 | 只索引 OCR 文本，丢失视觉和关系 |
| 用户看到无权文档 | ACL 继承和在线过滤 | 只在文档列表层过滤，Chunk 无权限字段 |
| 解析显示成功但无召回 | 输出质量门禁 | 空白或乱码未被识别为质量失败 |

## 17. 相似与易混概念

| 概念 | 核心差异 |
|---|---|
| 解析 vs OCR | 解析覆盖结构恢复；OCR 只是从图像识别文字的一步 |
| 清洗 vs 改写 | 清洗保持事实和定位；改写可能改变表达甚至语义 |
| 精确重复 vs 版本 | 相同内容可去重；版本还包含身份、时间和替代关系 |
| 元数据过滤 vs 正文检索 | 前者执行精确条件；后者计算内容相关性 |
| 文本 Caption vs 原图 | Caption 是派生描述，不能替代视觉证据 |
| 解析成功 vs 可用于 RAG | 无异常只说明程序执行；还需结构和下游检索质量合格 |
