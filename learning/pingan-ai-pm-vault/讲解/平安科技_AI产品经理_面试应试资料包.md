## 0. 给“应试 Agent”的使用说明

1. 每次回答先给结论，再分 3～5 点展开。
2. 单点尽量控制在 1～3 句话。
3. 技术问题必须说清：是什么、为什么、项目里怎么用、边界和风险。
4. 专业词第一次出现时，用一句中文解释。
5. 严格区分：
   - 【真实经历】：候选人实际做过；
   - 【公开事实】：公司或行业公开信息；
   - 【方案理解】：根据业务提出的设计，不得说成平安内部真实实现。
6. 不得编造金融从业经历、真实患者、线上 SLA、用户量、业务提升百分比或平安内部架构。
7. 产品问题优先按：**业务目标 → 用户/流程 → 数据 → AI 边界 → 技术方案 → 风险 → 指标 → MVP**。
8. 高风险金融/医疗场景中强调：**LLM 做理解、综合、解释、生成；确定性计算、权限、硬规则、正式审批保留给程序或人工。**

## 7. 津药达仁堂实习项目

### 【真实经历】项目定位

> **采购数据分析自动化 / 智能化项目。**

背景：
- 企业采购业务涉及 ERP / SRM；
- 多家企业数据来源分散；
- 字段定义和业务口径不统一；
- 原流程依赖人工下载 Excel、清洗、映射、修正、透视和分析。

### 核心痛点
- 多数据源；
- 字段不一致；
- 企业映射复杂；
- 业务指标口径不统一；
- 重复人工操作；
- 数据错误需要人工判断；
- 分析报告效率低。

### 核心方案

#### 1. 先做数据治理，而不是先上 LLM

**Source Data → Adapter → Canonical Schema → Analysis**

`Canonical Schema`：统一数据模型，把不同 ERP / SRM 字段先转成统一标准。

价值：
- 隔离不同系统差异；
- 源系统字段变化时只改 Adapter；
- 下游分析逻辑保持稳定。

#### 2. 明确 AI 与确定性程序边界

确定性任务：
- 金额计算；
- 聚合；
- Join；
- 指标计算；
- 映射；
- 透视；
- 去重。

交给 Python / openpyxl / 明确规则。

LLM 更适合：
- 理解分析意图；
- 判断调用哪个分析模块；
- 把自然语言转成结构化参数；
- 对确定性结果解释和总结。

核心原则：

> **不能因为用了大模型，就让 LLM 自己算采购金额和核心经营指标。**

#### 3. Structured Output

模型输出：
- 分析类型；
- 时间范围；
- 企业；
- 指标；
- 筛选条件。

再由后端：

**Schema Validation → Business Validation → Tool Execution。**

### 如果问“为什么不用 BI 就行？”

- 如果需求永远固定，BI + Python + RPA 足够；
- AI 的价值主要在自然语言需求、动态模块选择、结果解释、降低操作门槛；
- 不会为了“有 AI”强行做 Agent。

## 9. Health Agent 总体编排链路

核心思想：

> **固定 Workflow 控制主流程，LLM 只负责局部不确定性判断。**

简化链路：

**START  
→ initialize_run  
→ revalidate_scope / manifest / epoch  
→ classify_allowed_intent  
→ build_analysis_request  
→ plan_actions  
→ execute_read_only_tool  
→ stable_barrier  
→ synthesize  
→ validate_claims / citations / responsibility  
→ persist_terminal  
→ END**

### 术语

- `StateGraph`：用节点和边表达执行流程。
- `Node`：一个执行步骤。
- `Edge`：节点之间的执行关系。
- `Planning`：模型判断当前需要哪些允许的 Action / Tool。
- `Stable Barrier`：等待并行 Tool 完成后再统一进入综合。

为什么不用纯 ReAct 无限循环：

> Health Agent 是专项业务，风险更高、边界更清晰，所以采用 **Workflow 控制大框架 + LLM 有限自由**。

## 10. Hermes vs LangGraph

### Hermes

定位：

> **通用 Agent Runtime / Harness。**

核心：

**User → Conversation Loop → LLM → Tool Call → Tool Result → LLM → … → Final Answer**

特点：
- Conversation Loop；
- 通用 Tool Runtime；
- Prompt Assembly；
- Context Compression；
- Memory；
- Session Persistence；
- Retry / Provider Failover；
- Delegation / Subagent。

### Health Agent / LangGraph

定位：

> **领域专项 Agent Workflow。**

区别：
- Hermes：模型持续决定下一步；
- Health Agent：Graph 决定主流程；
- Hermes：messages 是执行核心之一；
- Health Agent：Typed State 更重要；
- Hermes：Memory / Compression 自己实现；
- LangGraph：提供 State / Checkpoint 基础设施，Memory 需要业务自己设计；
- Hermes：通用 Tool Runtime；
- Health：Tool Gateway + Scope + Authorization + Ledger，领域约束更强。

一句话：

> **Hermes 是自己造通用 Agent 执行引擎；LangGraph 是用 Graph 显式定义专项 Agent 的状态、流程和恢复规则。**

## 11. State / History / Memory / Context / Checkpoint

- `Session / Thread`：哪一次会话。
- `History`：过去说过什么。
- `State`：当前任务整体执行到了什么状态。
- `Checkpoint`：Graph 执行状态快照，用于恢复。
- `Memory`：从过去提取并长期保留、未来仍有价值的信息。
- `Model Context`：当前这一轮真正发给模型看的内容。

关键句：

> **数据库里存在，不代表这一轮 LLM 自动能看到。**

Health Agent 当前应准确描述为：
- Persistent Conversation；
- Bounded History；
- Graph State；
- Checkpoint；
- Domain Data；
- Knowledge Retrieval。

不要夸成已经有 Hermes 那种完整通用 Long-term Memory。

## 12. Tool Calling / Tool Gateway

### Tool Calling

模型只提出：
- Tool Name；
- Arguments。

真正是否执行由 Runtime 决定。

### Health Agent Tool 链路

**LLM Plan  
→ Frozen Tool Catalog  
→ AgentToolExecutor  
→ Tool Gateway  
→ Authorization  
→ Parameter Validation  
→ Handler  
→ Database / Service  
→ Frozen Result  
→ Agent**

### Frozen Tool Catalog

> 当前 Run 允许模型使用的 Tool 集合提前确定。

### Tool Gateway

> 所有 Tool 的统一受控入口。

承担：
- Tool 注册；
- 参数检查；
- 权限；
- Scope；
- 日志；
- Risk Control。

### Authorization Envelope

Tool Call 外的一层运行时授权信息，例如：
- User；
- Workspace；
- Role；
- Scope；
- Operation。

核心：

> **Prompt 是软约束，Runtime Authorization 才是硬约束。**

## 13. Ledger / Checkpoint / Outbox / Idempotency

### Ledger

这里不是区块链。

`AgentOperationLedger`：

> **持久化记录某个 Agent Operation 是否执行过、状态是什么、结果是什么。**

恢复链：

**Checkpoint 说 Tool 已完成  
→ 根据 Operation Key 找 Ledger  
→ 恢复 Frozen Result  
→ 校验 Result Hash  
→ 不重复执行。**

作用：
- Retry；
- Recovery；
- Idempotency。

### Checkpoint
> Graph 执行到了哪里。

### Ledger
> 这个具体 Operation 做过没有，结果是什么。

### Outbox
> 解决“数据库写成功，但消息发送失败”。

### Lease / Epoch / Fencing
- Lease：临时执行所有权；
- Epoch / Fencing Token：新接管者获得更高版本；
- 旧 Worker 即使复活，也不能继续写入。

## 14. RAG 链路

不要讲成“Embedding → Vector DB → GPT”。

完整理解：

**Source  
→ Parsing  
→ Chunk  
→ Metadata  
→ Generation / Version  
→ Index  
→ Query  
→ Filter  
→ FTS + Vector  
→ Fusion  
→ Top-K Evidence  
→ Citation  
→ Answer / No-answer**

### Health Agent 特点

#### Metadata-first
先根据：
- workspace；
- generation；
- space；
- license；
- document status；
- effective date

判断知识是否有资格参加检索。

#### Hybrid Retrieval
- FTS：全文 / 关键词；
- pgvector：语义向量；
- Fusion：融合两种排名。

#### Versioned Retrieval
一次 Run 固定 Knowledge Generation，避免同一次任务前后使用不同知识版本。

#### Citation
**Claim → Citation → Chunk → Source / Version。**

#### No-answer / Abstention
证据不足时明确拒绝做确定性结论。

## 15. RAG Evaluation

- Recall@5；
- MRR@5；
- Citation Correctness；
- No-answer Precision / Recall / F1；
- Generation Mismatch；
- Withdrawn Knowledge Leak；
- Cross-workspace Private Hit；
- Missing-license Publication。

解释：
- `Recall@K`：正确证据是否进入前 K；
- `MRR`：第一条正确证据排得有多靠前；
- `Citation Correctness`：引用是否真的支持 Claim；
- `No-answer`：证据不足时能否正确拒答。

## 18. Intent Recognition

**User → Intent Classifier → Refund / FAQ / Credit / Human**

### Hermes

**User → LLM 理解任务 → Tool Selection / Final Answer。**

即意图理解融合进 Reasoning + Tool Selection。

## 19. Agent Loop / Workflow Pattern

- `ReAct`：Reason → Action → Observation → Reason，边做边想。
- `Plan-and-Execute`：Planner → Plan → Executor → Replan，先规划后执行。
- `ReWOO`：先规划 Tool Dependency，再执行，减少反复调用 LLM。
- `Reflection / Reflexion`：Do → Evaluate → Reflect → Retry。
- `Evaluator-Optimizer`：Generator → Evaluator → 修改 → 合格。
- `Orchestrator-Workers`：总控拆任务，多 Worker 执行后聚合。

## 20. Multi-Agent

Multi-Agent 本质不是多开几个模型，而是解决：
- 谁拆任务；
- 谁分配；
- Context 怎么隔离；
- Agent 怎么通信；
- 谁汇总；
- 冲突怎么办；
- 谁拥有控制权；
- 成本怎么控制。

主要模式：

### Supervisor / Manager
**Manager → Specialist Agents → Manager Synthesis**

### Handoff
**Agent A → Agent B 接管对话**

### Router → Specialists
先识别任务，再进入专业 Agent。

### Fan-out / Fan-in
**一个任务 → 多 Agent 并行 → Reducer 聚合。**

### Hierarchical Multi-Agent
Supervisor 管 Supervisor。

### Hermes
`delegate_task`：

**Parent Agent → Child A/B/C → 每个 Child 独立 Conversation + Tool Loop → Summary 回 Parent → Parent 综合。**

原则：

> **复杂不等于一定 Multi-Agent，只有拆分和并行真正产生价值时才使用。**

## 23. 隐私计算

核心：

> **原始数据不适合直接暴露，但仍然希望联合计算。**

- `PSI`：隐私集合求交，找共同对象；
- `MPC`：多方安全计算，多方共同计算但减少原始输入暴露；
- `Federated Learning`：数据留本地，本地训练后聚合；
- `TEE`：可信执行环境，在硬件隔离环境中计算；
- `HE`：同态加密，在密文状态下执行特定计算；
- `Differential Privacy`：控制输出随机性，降低从结果反推个人信息的风险。

产品经理选型先问：
- 数据能否出域；
- 联合计算还是联合训练；
- 实时性；
- 安全要求；
- 性能；
- 成本；
- 参与方信任关系。

---

## 24. 金融 AI 场景共性设计

统一框架：

**业务目标  
→ 用户与现有流程  
→ 数据和 Evidence  
→ 确定性能力  
→ AI 插入点  
→ Tool / RAG / Workflow  
→ 权限 / Compliance / HITL  
→ Eval  
→ MVP  
→ Feedback Loop**

原则：

> **不要让 LLM 替代数据库、确定性计算、推荐/风控模型、硬规则或正式审批。**

---

## 25. 智能报告

传统能力：
- Data Warehouse；
- SQL；
- BI；
- 指标计算；
- 规则异常检测。

LLM 更适合：
- 数据解释；
- 趋势总结；
- 异常归纳；
- 报告生成；
- 跨来源信息综合。

风险：
- 数字幻觉；
- 错误归因；
- 指标口径过期；
- 引用错误。

原则：

> **数字 → SQL / Tool / Calculation Engine；解释 → LLM。**

---

## 26. 信贷风险 / 尽调 Agent

业务链：

**融资需求 → 材料提交 → 尽调 → 财务/非财务分析 → 风险判断 → 报告 → 审核/审批 → 放款/贷后。**

适合 LLM：
- 非结构化材料理解；
- 尽调信息抽取；
- 风险信息关联；
- 政策 RAG；
- 报告草稿；
- Missing Information 提示。

必须确定性 / 人工：
- 财务指标；
- 授信规则；
- 风险评分；
- 权限；
- 正式审批。

一句话：

> **LLM 可以辅助信贷决策，但不能成为无监督的最终审批者。**

---

## 27. 潜客推荐

关键：

> **“谁是潜客”本质主要是推荐 / 排序问题，不是生成问题。**

传统链：

**Customer Profile → Feature → Candidate Generation → Ranking / Propensity Model → Eligibility → Top-N。**

LLM 价值：
- 客户信息综合；
- 推荐原因解释；
- Why Now；
- Next Best Action；
- 客户经理沟通辅助。

风险：
- Suitability；
- Marketing Compliance；
- Privacy；
- 过度推荐。

---

## 28. Hallucination Control

完整治理：

**Source Governance  
→ Retrieval / Tool Grounding  
→ Prompt Constraint  
→ Structured Output  
→ Validator  
→ Citation  
→ Abstention  
→ HITL  
→ Eval。**

- `Grounding`：回答建立在真实 Evidence / Tool Result 上。
- `Validator`：程序检查模型输出。
- `Abstention`：证据不足时拒绝给确定性结论。
- `HITL`：高风险节点由人确认。

## 34. 项目推进问题

如果业务、研发、算法意见冲突：

1. 回到业务目标；

## 35. MVP 思维

`MVP`：Minimum Viable Product，最小可行产品。

不是“做个很差的简版”，而是：

> **用最小成本验证最关键的业务假设。**

例：信贷 Agent MVP
- 固定一个贷款类型；
- 固定一套材料；
- 固定一版报告；
- 只做辅助分析；
- 不直接进入审批；
- Shadow Test；
- 收集人工修改率。

## 39. 高频关键句

- **产品经理：** 把模糊业务问题变成可落地、可验收的产品方案。
- **AI PM：** 决定什么应该交给模型，什么必须由确定性系统或人工完成。
- **Agent：** LLM + State + Tool + Knowledge + Control。
- **Workflow：** 代码定义整体路径。
- **Agent Loop：** 模型根据环境反馈持续决定下一步。
- **LangGraph：** 显式管理 State、Control Flow 和 Checkpoint。
- **Hermes：** 通用 Agent Harness / Runtime。
- **Memory：** 长期有价值的信息，不等于历史记录或 Checkpoint。
- **Context：** 当前一次模型调用真正能看到的信息。
- **Tool Calling：** 模型提出工具调用请求，Runtime 决定是否执行。
- **RAG：** 证据检索 + 生成，而不只是向量数据库。
- **Grounding：** 让模型结论基于可验证证据。
- **Citation：** 让 Claim 可追溯到 Source。
- **Ledger：** 记录业务 Operation 是否执行过以及结果，用于幂等和恢复。
- **Checkpoint：** 记录 Graph 执行到哪里。
- **Intent：** 将自然语言需求映射到业务路径。
- **Multi-Agent：** 多个独立 Context / 能力边界 Agent 的协调问题。
- **可信数据空间：** 多主体在可信规则下进行数据协作。
- **隐私计算：** 数据不能直接暴露时仍支持联合计算。
- **金融 AI：** LLM 做理解与综合，风控规则、计算和正式审批保留确定性控制。
