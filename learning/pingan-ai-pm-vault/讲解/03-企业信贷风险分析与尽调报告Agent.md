# 企业信贷风险分析与尽调报告 Agent：真实业务场景完整讲解

> 本文不是把“RAG + Agent + 大模型”套到一个虚构金融故事上，而是以**商业银行企业授信/流动资金贷款的真实业务流程**为基础，再讨论大模型和 Agent 可以在哪些环节产生价值。
>
> 阅读时始终区分三层：
>
> - **【行业事实】**：监管文件、银行公开报告能够支持的事实；
> - **【产品方案】**：基于这些事实设计的一套合理 AI 产品方案，不声称平安内部一定这样实现；
> - **【个人映射】**：你已有项目能够证明的方法论，不包装成做过银行信贷项目。

---

## 1. 场景题应该怎么问才真实

面试官可能把问题问成：

> **如果让你设计一个面向银行对公信贷人员的“企业尽调与风险分析 Agent”，帮助客户经理完成企业资料核验、风险分析和尽职调查报告生成，你会怎么设计？**

这不是凭空创造出来的方向。

### 【行业事实】平安银行已经公开披露类似场景

平安银行《2025 年第三季度报告》披露：对公业务在**客户商机挖掘、尽职调查报告生成**等重点领域上线智能助手；风控合规方面建立 AI 风险中台，将智能体嵌入风险管理流程，以提升信贷全流程业务处理及风险决策效率。

到 2026 年，平安银行公开披露的方向又进一步推进：

- 对公业务持续建设**风险专家知识库**，推动 AI 能力嵌入信贷流程；
- 零售领域则已经公开提到尽调、审批、放款、催收等智能体的人机协同应用。

因此，“尽调报告 Agent / 信贷风险 Agent”确实属于银行正在落地的大模型场景，而不是为了面试临时编出的功能。

**公开来源：**

  https://pdf.dfcfw.com/pdf/H2_AN202510241768245755_1.pdf
- 平安银行 2026 年第一季度报告相关披露：  
  https://www.hkexnews.hk/listedco/listconews/sehk/2026/0424/2026042403295_c.pdf
- 平安银行 2026 年半年度报告公开信息：

# 2. 先别谈 AI：真实的企业信贷到底在做什么

企业申请银行授信，不是“提交几个 PDF → 银行决定批不批”。

从产品视角，可以先把流程理解成：

```text
企业融资需求
    ↓
业务受理
    ↓
客户调查 / 尽职调查
    ↓
财务与非财务风险分析
    ↓
信用评价 / 授信方案
    ↓
风险审查与审批
    ↓
合同签署
    ↓
放款 / 支付审核
    ↓
贷后监测
```

不同银行组织名称、具体系统和审批层级会不同，但这条“贷前调查 → 风险评价 → 审批 → 放款 → 贷后”的主线有明确监管基础。

2024 年施行的《流动资金贷款管理办法》要求银行：

- 实行贷款**全流程管理**；
- 全面了解客户信息；
- 建立风险管理制度和岗位制衡机制；
- 评定客户信用等级；
- 根据经营规模、业务特征、资金循环周期等测算营运资金需求；
- 按照**贷审分离、分级审批**原则建立评审流程；
- 放款前确认提款条件；
- 对贷款用途和资金支付实施管理；
- 贷款后持续评估经营状况和还款能力。

来源：  
https://www.gov.cn/gongbao/2024/issue_11306/202404/content_6947721.html

这说明一个非常重要的产品结论：

> **信贷不是一次模型推理，而是一条有岗位分工、有证据、有规则、有审批、有持续监控的业务流程。**

所以我们设计的不是：

```text
企业材料 → GPT → 批 / 不批
```

而应该是：

```text
已有信贷流程
      +
AI 对其中高耗时、非结构化、知识密集的环节做增强
```

# 3. “尽调”到底在调查什么

《商业银行授信工作尽职指引》对授信调查和分析给出了非常具体的要求。

### 【行业事实】银行需要核实而不是只“阅读材料”

授信调查需要关注和验证的内容包括：

```text
主体与资格
├─ 企业身份
├─ 授信主体资格
├─ 股权 / 关联客户
└─ 资料合法性、真实性、有效性

财务因素
├─ 财务报表
├─ 盈利能力
├─ 现金流
├─ 偿债能力
├─ 融资和负债
└─ 资金需求

非财务因素
├─ 公司治理
├─ 管理层
├─ 履约记录
├─ 产品与市场
├─ 行业特征
├─ 竞争能力
└─ 宏观环境

第二还款来源
├─ 保证人
├─ 抵押物
└─ 质押物

最终
└─ 形成书面的分析评价报告
```

监管指引还明确要求对客户财务因素、非财务因素、信用等级、担保情况等进行分析，并形成书面的分析评价报告。

来源：

- 上海市发展改革委公开的《商业银行授信工作尽职指引》相关内容：  
  https://fgw.sh.gov.cn/ys-hqjrfw-1.1.1.1/
- 指引原始附件公开版：  
  https://fgw.sh.gov.cn/cmsres/82/8294942ccaef4bdfb40dd22e18d3f59c/04c522136bc6274c13ec74c9bda51674.pdf

这也解释了为什么“尽调报告生成”天然适合成为大模型场景：

> 其中有大量**材料阅读、字段抽取、跨文档比对、规则核对、非结构化信息归纳和文字撰写**。

这些正是 LLM 比传统固定规则更有优势的部分。

但它仍然只是完整信贷决策链的一部分。

# 4. 这道题最重要的第一条判断：不要让 LLM 直接决定授信

如果回答成：

```text
把企业经营信息、财报和征信给大模型
→ 大模型判断风险
→ 输出是否授信
```

这个方案在真实银行场景中是不成立的。

原因不是“大模型还不够聪明”这么简单，而是三层问题。

## 第一层：信贷本来就有确定性的规则、模型和审批体系

真实风险决策通常会同时依赖：

```text
信贷政策 / 准入规则
+
客户评级
+
额度与资金需求测算
+
传统风险模型 / 评分模型
+
授信人员专业判断
+
审批授权体系
```

LLM 不应该替代所有这些机制。

尤其财务比率、营运资金需求、授信额度、风险限额等确定性计算，应该由确定性程序完成，而不是让模型自由计算。

---

## 第二层：AI 生成结果本身存在不可靠性

LLM 可能：

- 抽错金额；
- 把不同会计期间混在一起；
- 把母公司和子公司数据混淆；
- 忽略否定句；
- 把“尚未发生”总结成“已经发生”；
- 在没有证据时补全原因；
- 引用一个看似存在、实际不存在的政策条文。

这些问题放在普通文案里可能只是质量问题，放在信贷中可能变成风险决策问题。

---

## 第三层：监管已经把信贷审批明确放入高风险 AI 场景

2026 年 6 月，国家金融监督管理总局发布《关于银行业保险业人工智能安全开发应用的指导意见》。

其中明确提出：

> 涉及资金交易、资产评估、**信贷审批**、承保理赔、风险管理等场景属于高风险人工智能应用，需要加强准入、运行监测，并在关键环节建立人工监督和干预机制。

指导意见同时要求金融机构：

- 科学设定 AI 的功能边界；
- 设定系统和数据权限；
- 完善人机协同流程；
- 明确岗位责任；
- 建立人工监督和干预；
- 设置紧急停用、模型退出和人工替代机制。

来源：

- 国家金融监管总局政策信息：  
  https://www.nfra.gov.cn/en/view/pages/ItemDetail.html?docId=1264488
- 指导意见公开全文：  
  https://policy.mofcom.gov.cn/claw/clawContent.shtml?id=106182

因此正确定位应该是：

> **LLM / Agent 是风险分析和作业辅助层，而不是无约束的最终授信决策者。**

# 5. 那么 Agent 真正应该解决什么问题

先站在信贷人员角度看问题。

一个企业客户的尽调可能面对：

```text
工商 / 主体资料
财务报表
银行流水
授信申请材料
担保材料
合同
发票 / 订单
历史信贷记录
内部客户信息
行业资料
银行内部制度
现场调查记录
```

传统工作中，高耗时部分往往不是某一个公式，而是：

```text
资料散落
   ↓
手工找信息
   ↓
复制字段
   ↓
跨材料核对
   ↓
发现异常
   ↓
查内部政策
   ↓
写报告
   ↓
审查人员再重新找证据
```

### 【产品方案】Agent 的核心目标

不是“替人审批”，而是：

> **把“找资料—核资料—算指标—查规则—识别异常—形成有证据的报告草稿”串成一条受控的辅助流程。**

我们可以把产品目标定义为：

```text
降低材料处理时间
+
减少低级数据错误
+
提高风险信息覆盖
+
让每个结论可回到证据
+
减少报告机械撰写工作
+
但保留人工尽调与审批责任
```

这才符合真实业务。

# 6. 一个合理的企业尽调 Agent 总体架构

```text
                企业提交材料 / 银行内部数据
                           ↓
                 Document Ingestion
                           ↓
          OCR / Parser / Table Extraction
                           ↓
                 统一证据与字段层
                           ↓
        ┌──────────────────┼──────────────────┐
        ↓                  ↓                  ↓
  Deterministic Tools     RAG            External / Internal
  财务计算、比率、      信贷政策、        Authorized Tools
  资金需求测算           行业政策等        工商/内部系统等
        └──────────────────┼──────────────────┘
                           ↓
                    Agent Orchestrator
                           ↓
              风险点识别 / 资料缺口 / 比对
                           ↓
                   Structured Risk Draft
                           ↓
                 尽调报告草稿 + Evidence
                           ↓
                    人工复核 / 修改
                           ↓
                   进入正式审查审批
```

这里有一个核心设计原则：

> **事实从 Tool / 数据源 / 原文证据来；计算由确定性程序来；LLM 负责理解、关联、归纳、解释和撰写。**

# 7. 第一步：材料接入，不要直接把一堆 PDF 扔给 LLM

真实企业材料经常包含：

- 扫描 PDF；
- 财务报表；
- Excel；
- 图片；
- 合同；
- 多页表格；
- 格式各异的证明材料。

所以第一层是 Document Intelligence，而不是 Agent 自由推理。

```text
文件上传
   ↓
MIME / 完整性检查
   ↓
OCR / 文档解析
   ↓
页面、段落、表格识别
   ↓
字段抽取
   ↓
原文位置锚点
   ↓
结构化证据对象
```

例如不能只得到：

```json
{
  "revenue": 120000000
}
```

最好同时保留：

```json
{
  "field": "revenue",
  "value": 120000000,
  "period": "2025",
  "unit": "CNY",
  "source_document": "2025_audited_financial_statement.pdf",
  "page": 18,
  "table": "利润表",
  "extraction_status": "verified"
}
```

为什么？

因为信贷人员后面一定会问：

> **这个数字从哪里来的？**

所以在金融场景中，Structured Output 的目的不只是方便后端解析，还要服务**可追溯性**。

---

# 8. 第二步：统一数据层，解决“同一个东西叫法不同”

不同材料可能写：

```text
营业收入
主营业务收入
销售收入
Revenue
```

也可能存在：

```text
万元
元
百万元
```

甚至：

```text
2024 年
2024 年度
截至 2024-12-31
```

如果不先规范化，大模型很容易把不同口径混在一起。

所以要有一个 Canonical Schema，例如：

```text
company
financial_period
statement_type
metric_code
metric_name
value
unit
currency
source_id
source_location
verification_status
```

这一步和你津药项目中做统一采购数据模型的思想非常接近：

> **先把异构数据转成稳定 Schema，再让智能层使用。**

### 【个人映射】

这里你可以诚实地说：

> 我没有做过银行授信数据模型，但在津药 ERP / SRM 项目中做过多源字段、业务口径和数据粒度统一，所以我会把同样的数据治理思想迁移到企业信贷材料层，而不是让大模型直接面对未经治理的异构数据。

这叫“方法论迁移”，不是编项目经验。

---

# 9. 第三步：确定性计算交给 Tool，不交给 LLM

假设需要分析：

```text
流动比率
速动比率
资产负债率
应收账款周转
存货周转
经营现金流变化
营运资金缺口
```

正确链路：

```text
LLM / Workflow
判断当前需要某项分析
       ↓
Financial Analysis Tool
       ↓
读取经过核验的结构化字段
       ↓
确定性公式计算
       ↓
返回结果 + 输入来源 + 公式版本
       ↓
LLM 做业务解释
```

而不是：

```text
把三年财报贴进 Prompt
→ “请你计算资产负债率并分析”
```

原因很简单：

> **数字计算应该可复现。**

2024 年《流动资金贷款管理办法》甚至提供了营运资金需求量的测算思路，要求结合销售收入、利润率、存货、应收、应付等因素合理估算资金需求。

这进一步说明：

> 信贷中的金额和比率不是“语言生成问题”，而是确定性业务计算问题。

---

# 10. 第四步：RAG 应该查什么

这类 Agent 的 RAG 不是用来查询客户实时余额的。

实时客户数据应该来自 Tool / Database。

RAG 更适合：

```text
银行信贷政策
产品准入规则
行业授信政策
风险管理制度
尽调操作规范
内部报告模板
监管制度
行业知识
```

例如 Agent 发现：

```text
客户属于某行业
+
申请某种贷款
```

可以检索：

```text
当前版本的行业授信政策
+
对应产品的准入规则
```

然后把政策条款作为 Evidence 返回。

这里必须做**版本控制**。

因为信贷政策会更新。

报告中最好记录：

```text
policy_id
policy_version
effective_date
retrieved_chunk
source_anchor
```

这样以后复核时能回答：

> 当时依据的是哪个版本的制度？

---

# 11. 第五步：Tool Calling 应该怎么设计

一个真实可用的尽调 Agent，不应该拥有一个万能工具：

```text
query_everything()
```

而应该拆成权限和职责清晰的能力。

示意：

```text
get_customer_master()
get_financial_statements()
calculate_financial_ratios()
calculate_working_capital_need()
get_existing_credit_exposure()
get_related_party_information()
get_collateral_information()
search_credit_policy()
search_industry_policy()
get_previous_due_diligence_record()
```

注意：

这些名字是【产品方案示意】，不是在声称平安内部就使用这些接口。

---

# 12. Tool Calling 的权限不能交给 Prompt

例如 Agent 生成：

```json
{
  "tool": "get_existing_credit_exposure",
  "arguments": {
    "customer_id": "C001"
  }
}
```

真正执行前 Runtime 仍要检查：

```text
调用人是谁？
    ↓
是否属于这个授信任务？
    ↓
当前岗位能否访问这类数据？
    ↓
是否有客户 / 项目 Scope？
    ↓
数据级别是否允许用于当前用途？
    ↓
是否需要脱敏？
```

《银行保险机构数据安全管理办法》明确要求：

- 对敏感级及以上数据实行“**业务必要授权**”；
- 建立数据访问闭环管理；
- 对访问行为实施审计；
- 对敏感数据加工、汇聚、分析采取必要保护措施；
- 对用户认证、访问控制、日志审计等提出要求。

来源：  
https://app.www.gov.cn/govdata/gov/202412/29/523120/article.html

所以：

```text
Prompt：
“只能看你有权限的数据”
```

只是软约束。

真正安全的是：

```text
Identity
+
Role
+
Task Scope
+
Data Classification
+
Authorization
+
Audit Log
```

这些都必须在 Runtime 层实现。

---

# 13. 第六步：Agent 到底“分析”什么

经过数据、计算和政策检索以后，LLM 最适合做的事情开始出现。

例如：

### 跨材料一致性检查

```text
审计报告：营业收入 1.20 亿
纳税材料：相关收入规模明显不同
客户申请书：填报 1.65 亿
```

Agent 可以识别：

```text
多个来源存在显著差异
```

但不要马上得出：

```text
客户造假
```

正确输出应该是：

```text
发现不一致
+
列出每个来源
+
提示需要人工核实
```

---

### 时间序列变化解释

例如程序先算出：

```text
应收账款增长 60%
营业收入增长 8%
经营现金流明显下降
```

LLM 可以进一步帮助信贷人员组织成：

```text
应收账款增速显著高于收入增速，
同时经营现金流下降，
建议进一步核实回款周期、主要客户集中度及账龄情况。
```

这里 LLM 的价值是：

> **把多个确定性指标连接成可调查的问题。**

不是替代风险人员给出最终结论。

---

### 资料缺口识别

根据授信类型和制度要求，Agent 可以输出：

```text
缺少：
- 最新一期财务报表
- 某担保材料
- 某关联企业说明
```

这是非常实用的 Agent 场景。

因为它将：

```text
制度要求
+
当前文件清单
```

做了动态比对。

---

# 14. Structured Output：风险分析不能只返回一篇作文

比起：

```text
“该企业整体经营情况较好，但存在一定风险……”
```

应该先形成结构化 Risk Finding：

```json
{
  "risk_id": "RF-001",
  "category": "cash_flow",
  "severity": "review_required",
  "statement": "经营现金流下降且应收账款增长较快，需要进一步核实回款质量",
  "evidence": [
    {
      "source_id": "FS-2025",
      "location": "cash_flow_statement"
    },
    {
      "source_id": "FS-2025",
      "location": "balance_sheet"
    }
  ],
  "calculated_metrics": [
    "receivable_growth_rate",
    "operating_cashflow_change"
  ],
  "policy_refs": [],
  "missing_information": [
    "应收账款账龄"
  ],
  "needs_human_review": true
}
```

然后再由这些 Risk Findings 生成报告。

于是整个报告可以做到：

```text
报告文字
   ↕
结构化 Risk Finding
   ↕
指标 / Tool Result
   ↕
原始证据
```

这比单纯让模型写一篇流畅的报告可靠得多。

---

# 15. 尽调报告 Agent 应该生成“草稿”，不是直接生成正式结论

产品界面建议不要只有：

```text
[生成报告]
```

更合理的是一个 Due Diligence Workbench：

```text
┌─────────────────────────────────────────┐
│ 企业尽调工作台                          │
├─────────────────────────────────────────┤
│ 资料完整度    发现风险项    待人工核验  │
│   86%            7            4         │
├─────────────────────────────────────────┤
│ 左：材料 / Evidence                     │
│ 中：风险发现 / Missing Info             │
│ 右：报告草稿                            │
│                                         │
│ 点击任一结论 → 跳到原始来源             │
└─────────────────────────────────────────┘
```

核心交互：

```text
查看原文
接受风险点
驳回风险点
补充材料
修改结论
重新分析指定章节
生成报告草稿
提交人工审查
```

产品原则：

> **让 AI 降低查找和写作成本，但不要隐藏证据和人的责任。**

---

# 16. Human-in-the-loop 应该放在哪里

不是只在最后放一个：

```text
[我确认]
```

应该按风险设置不同人工节点。

例如：

```text
文件解析低置信度
→ 人工确认字段

来源冲突
→ 人工核验

重大风险识别
→ 风险人员确认

模型建议调整授信判断
→ 只能作为辅助信息

正式审批
→ 按原有授权体系完成
```

2026 年金融监管关于 AI 的指导意见明确要求高风险场景建立人工监督和干预机制。

所以产品方案中必须主动提出：

> **AI 可以提前完成“准备工作”和“辅助分析”，但正式授信审批仍进入既有审查审批体系。**

---

# 17. 最终授信决策里，传统风控模型和 LLM 怎么分工

这是很可能被追问的地方。

可以这样理解：

```text
传统模型 / 规则
适合：
- 风险概率
- 评分
- 阈值
- 客群分层
- 准入
- 欺诈特征
- 稳定量化信号

LLM
适合：
- 非结构化材料理解
- 信息抽取
- 跨文档关联
- 风险点归纳
- 规则解释
- 报告生成
- 交互式辅助分析
```

两者不是替代关系。

更合理的是：

```text
Structured Data
      ↓
Rule / Risk Model ─────────────┐
                              ↓
Unstructured Data → LLM → Risk Evidence
                              ↓
Policy / RAG ──────────────────┤
                              ↓
                  Human Risk Review
                              ↓
                     Existing Approval
```

---

# 18. 幻觉治理在这个场景必须具体到“证据”

不能只说：

```text
用 RAG 降低幻觉
```

要拆开。

## 18.1 数字不能靠模型记忆

财务数字：

```text
必须来自已核验字段 / Tool
```

---

## 18.2 计算不能自由生成

比率、额度、资金需求：

```text
Deterministic Tool
```

---

## 18.3 政策必须有版本和引用

```text
RAG
+
policy_version
+
source_anchor
```

---

## 18.4 结论必须绑定 Evidence

不能：

```text
“企业偿债能力下降”
```

而应该知道：

```text
结论依据了哪些指标、哪些文档、哪一页
```

---

## 18.5 证据不足时必须允许 Abstain

例如：

```text
缺少最近一期现金流量表
```

系统应该：

```text
无法完成该项判断，需要补充材料
```

而不是让模型根据其他内容猜。

---

# 19. 一个非常关键的机制：事实、推断、建议要分开

报告里最好不要把所有文本混成一段。

建议分成：

```text
Fact
确定事实 / 结构化数据

Derived Metric
系统计算结果

Observation
发现的异常或关系

Hypothesis
可能原因，需要进一步核实

Recommendation
建议调查动作

Human Conclusion
人工最终判断
```

例如：

```text
Fact:
2025 年末应收账款为 X。

Derived Metric:
同比增长 Y%。

Observation:
应收增速明显高于营业收入增速。

Hypothesis:
可能存在回款周期拉长等情况。

Recommendation:
核实账龄结构及前五大应收客户。

Human Conclusion:
由信贷人员填写。
```

这会比让 LLM 直接写：

> “该企业回款能力恶化。”

可靠得多。

---

# 20. 如何防止 Prompt Injection 和恶意材料影响 Agent

这是企业 Agent 比普通 Chatbot 多出来的问题。

企业上传的文件本身可能包含：

```text
Ignore previous instructions...
```

或者 PDF 里出现一段与业务无关的指令。

因此：

```text
文档内容
≠
System Instruction
```

需要把外部文档当作**不可信数据**处理：

```text
解析后的材料
→ 仅进入 Evidence / Context
→ 不允许改变 Agent 权限
→ 不允许直接触发 Tool
```

Tool 执行权限依旧由 Runtime 决定。

金融场景中特别不能出现：

```text
文件中的一句话
→ 改变工具授权
```

# 21. 贷后阶段为什么也适合 Agent

企业信用风险不是审批完成就结束。

真实信贷管理还包括贷后监测。

可以继续构建：

```text
企业经营数据变化
外部重大事件
账户与还款表现
行业变化
担保变化
        ↓
Risk Monitoring
        ↓
触发异常
        ↓
Agent 汇集证据
        ↓
生成风险事件摘要
        ↓
人工判断是否需要进一步行动
```

《商业银行授信工作尽职指引》本身就要求，在影响客户资信的重大事项发生时重新进行授信分析评价，例如：

- 重大政策变化；
- 股权或管理层变化；
- 财务收支能力重大变化；
- 重大诉讼；
- 交叉违约等。

所以 Agent 不应该被理解成“生成一次报告的按钮”，而可以进入**信贷生命周期**。

不过本题若时间有限，应先把贷前尽调讲清楚，再把贷后监测作为扩展。


这些指标在金融产品里不是附属项，而是核心验收条件。

# 23. MVP 应该从哪里开始

不要第一版就做：

```text
全自动信贷 Agent
```

更合理的 MVP：

```text
固定一种企业贷款类型
+
固定一套材料清单
+
只做贷前尽调辅助
+
三个核心能力：
1. 材料抽取
2. 风险点 + 资料缺口
3. 有引用的尽调报告草稿
```

并明确：

```text
No Auto Approval
No Autonomous Loan Decision
No Automatic Formal Record Modification
```

为什么这样切？

因为它：

- 业务价值明确；
- 使用频率高；
- 能拿到人工对照结果；
- 风险比自动审批低；
- 容易建立评测集；
- 能逐步积累银行内部高质量知识和 Badcase。

# 24. 一个真实的试点方式

例如选一个业务团队，做 Shadow / Assist 模式：

```text
原流程继续运行
        +
AI 同步生成结果
```

第一阶段不直接改变审批。

对比：

```text
人工发现了哪些风险？
AI 发现了哪些风险？

人工报告有哪些内容？
AI 草稿遗漏 / 错误了什么？

人工用了多久？
AI 辅助后用了多久？
```

确认质量以后，再进入：

```text
AI Draft → 人工正式使用
```

最后才逐步扩大范围。

这比：

```text
上线一个 Chatbot → 看用户喜不喜欢
```

更符合高风险金融应用。

# 25. 面试中可以直接说的完整回答

下面是一版适合现场表达的回答，不要求逐字背。

> 如果让我设计企业信贷风险分析或尽调报告 Agent，我会先把它放回真实的授信流程里看，而不是直接做一个“大模型审批系统”。
>
> 企业授信本身包含客户调查、财务和非财务分析、信用评价、审查审批、放款和贷后管理，而且要求贷审分离和分级审批。因此我会把大模型定位成尽调和风险分析的辅助层，而不是最终授信决策者。
>
> 第一层先做材料和数据治理。企业会提交财报、合同、担保材料等大量异构文件，我会通过 OCR、文档解析和统一 Schema 把关键字段结构化，同时保留来源文档、页码和表格位置，保证后面每一个结论都能回溯证据。
>
> 第二层把确定性计算和实时数据访问做成 Tool。比如财务比率、营运资金需求、现有授信敞口等，不让 LLM 自己算，而是由确定性服务执行。银行内部信贷政策、行业政策等则通过带版本的 RAG 获取。
>
> 第三层再让 Agent 做它擅长的事情，比如跨文档比对、识别信息不一致、发现资料缺口、把多个指标组织成风险调查问题，并生成结构化 Risk Findings。每个风险点必须带 Evidence、缺失信息和是否需要人工复核，最后再根据这些结构化结果生成尽调报告草稿。
>
> 权限上，我不会靠 Prompt 约束模型。Tool Runtime 要根据真实用户身份、岗位、授信任务 Scope 和数据等级做授权与审计。对于高风险节点，必须保留人工监督。尤其 2026 年金融监管已经把信贷审批列为高风险 AI 应用，所以 AI 可以提高尽调和风险分析效率，但正式审批仍应进入银行既有的授权和人机协同流程。
>
> 第一版我不会做全自动授信，而会先选固定贷款类型做 Shadow Pilot，重点验证字段抽取、风险点召回、引用准确率、人工修改率和尽调时间下降，再决定是否扩大场景。
>
> 我认为这个产品真正的价值不是“帮客户经理写一篇报告”，而是把原来分散在材料、数据、制度和系统里的信息串成一条可追溯的风险分析链，同时保持最终责任在人和正式审批体系中。

# 26. 面试官继续追问时怎么答

## 追问 1：为什么不能让大模型直接做信用评分？

因为信用评分是需要稳定校准、可验证和持续监控的量化风险问题，已有规则、统计模型和机器学习模型更适合作为核心量化能力。

LLM 更适合处理非结构化材料、文本理解和解释。

可以组合，但不能把“语言模型的一个生成分数”直接当违约概率。

---

## 追问 2：如果 AI 和传统风险模型结论冲突怎么办？

不要规定：

```text
AI 优先
```

也不要规定：

```text
传统模型永远优先
```

应该拆来源：

```text
传统模型：
量化评分信号

AI：
非结构化风险 Evidence

规则：
硬性准入

人工：
综合决策
```

如果冲突：

```text
显式展示冲突
→ 给出各自依据
→ 触发人工 Review
```

不能静默覆盖。

---

## 追问 3：RAG 能解决幻觉吗？

只能降低一部分无依据生成。

还需要：

```text
Tool Grounding
Structured Output
Citation
Deterministic Calculation
Abstention
Human Review
Evaluation
```

尤其财务数据不能只依靠 RAG 文本片段。

---

## 追问 4：模型怎么知道某个风险真的存在？

模型不应该凭感觉给结论。

一个风险点至少应连接：

```text
Evidence
+
Derived Metric
+
Policy / Rule（如适用）
+
Reason
```

如果缺少关键证据：

```text
Needs Further Investigation
```

而不是强行下结论。

---

## 追问 5：怎么评价“风险发现”能力？

不能只测答案像不像。

要建立历史案例 / 专家标注集，并按风险类型衡量：

```text
Precision
Recall
重大风险 Recall
Evidence Correctness
False Positive
```

同时按：

```text
财务风险
行业风险
关联风险
担保风险
资料一致性
```

分别评测，才能做失败归因。

---

## 追问 6：怎么处理长达几百页的尽调材料？

不要一次全部塞进 Context。

更合理的是：

```text
Document Parsing
→ Hierarchical Chunking
→ Structured Extraction
→ Document / Section Index
→ 按任务检索相关 Evidence
→ 必要时 Map-Reduce / Section Summary
→ 最终报告
```

财务表格应优先结构化，不要把整个表格仅当普通文本 Chunk。

---

## 追问 7：Agent 为什么比普通 Workflow 有价值？

如果步骤完全固定：

```text
解析 → 算指标 → 套模板
```

Workflow 就足够。

Agent 的价值出现在：

```text
某个风险出现后
→ 动态决定还需要查什么
→ 调哪个 Tool
→ 查哪条制度
→ 发现缺口后继续补证
```

因此更合理的方案仍然是：

> **Workflow 控制主流程，Agent 在调查和分析节点内做受控决策。**

---

# 27. 与 Hermes / LangGraph 的技术思想怎么连接

这道业务题不要求你说“我们用 Hermes”。

但学习时可以映射：

```text
LangGraph / Workflow
控制：
材料处理 → 分析 → Review → Report

Agent Loop
控制：
当前风险点是否需要继续查 Tool / RAG

Tool Schema
定义：
数据和能力怎么被模型请求

Runtime Context
携带：
user / role / task_id / scope

State
保存：
当前案件的分析中间状态

Checkpoint
保存：
任务执行进度

Approval
控制：
高风险操作是否允许执行
```

Hermes 给你的启发尤其是：

> 模型产生 Tool Call 不等于 Tool 必须执行。

真正的 Runtime 仍然可以：

```text
过滤 Tool
检查 availability
拦截危险操作
要求 approval
记录结果
```

在银行里，这个思想要进一步升级成：

```text
身份
+
权限
+
数据 Scope
+
业务规则
+
审计
+
人工审批
```

# 28. 与你个人经历怎样连接，但不造假

## 津药 ERP / SRM 项目

你真正能映射的是：

```text
异构业务数据
→ 统一字段 / 统一口径 / Schema

确定性金额和聚合
→ Tool 而不是 LLM

LLM
→ 理解任务 / 选择分析模块 / 解释结果
```

迁移到信贷就是：

```text
企业异构材料
→ 信贷统一 Evidence Schema

财务比率 / 营运资金
→ Deterministic Tool

LLM
→ 风险材料理解 / 解释 / 报告
```

不要说：

> 我做过金融风控。

应该说：

> 我虽然没有直接做过银行信贷项目，但数据治理、LLM 与确定性计算分层、结构化输出这些设计方法我在真实企业数据项目中实践过。

---

## Personal Health Agent

能映射：

```text
Tool Authorization
Citation
Evidence
明确确认
受控 Provider
```

这些与信贷 Agent 的：

```text
Authorization
Evidence Traceability
Human Review
Fail-closed
```

是一类工程思想。

但不要把健康 Agent 包装成金融生产经验。

---

# 29. 这道题真正应该记住的框架

不是背 20 个组件。

只要脑中有这一条：

```text
真实信贷流程
    ↓
材料 / 数据治理
    ↓
确定性规则、计算、传统风险模型
    ↓
Agent 处理非结构化信息与动态调查
    ↓
RAG 提供制度知识
    ↓
所有结论绑定 Evidence
    ↓
结构化风险发现
    ↓
尽调报告草稿
    ↓
人工风险审查
    ↓
既有审批体系
```

一句话总结：

> **信贷 Agent 的目标不是把授信决策交给 LLM，而是把信贷人员原本大量花在“找资料、核资料、算指标、查制度、写报告”上的工作变成一条可追溯、可验证、受权限控制的 AI 辅助链路。**

这才是一个真实金融场景下比较成立的大模型产品方案。
