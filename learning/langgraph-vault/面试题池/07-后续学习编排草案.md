# 后续学习编排草案

这不是正式答案目录，而是根据公开面试题研究和 20 条深度主链得到的**学习结构草案**。

核心原则：

> 不按 69 道题逐题孤立刷，也不删除任何题；每次学习一个主问题，把相关原题作为连续追问展开。

## 建议分成两大阶段

### Part 4：核心机制 + 综合项目深挖

先解决“面试官围绕你的 LangGraph 项目会怎么一路追问”。建议主线：

```text
M01 框架选型
→ M02 完整执行链
→ M03 Graph 拆分边界
→ M04 State 契约
→ M05 Reducer / Super-step / 并行
→ M06 Control Flow
→ M07 Thread / Checkpoint / Memory
→ M08 Resume / Replay
```

这部分不是重新讲基础定义，而是每道主问题都必须回答：

```text
口头主回答
→ 完整机制
→ 采购经营 Agent 中的真实例子
→ State / 数据具体怎么变化
→ 关键代码
→ 追问题
→ 边界与 trade-off
```

Part 4 完成后，应该能应付“为什么这么设计”和“框架内部到底怎么跑”的连续深挖。

### Part 5：生产级 Agent Engineering

再进入真正拉开工程差距的主线：

```text
M09 外部副作用 / 幂等 / 对账
→ M10 持久化规模与版本升级
→ M11 错误分类 / Retry / Fallback
→ M12 并发 / 部分成功 / Cancel
→ M13 高并发部署
→ M14 Observability / Debugging
→ M15 Evaluation
→ M16 Streaming / Frontend
→ M17 Context / Cost / Latency
→ M18 Injection / Authorization / Tool Policy
→ M19 Secret / Sandbox / Multi-tenancy
→ M20 Multi-Agent 综合系统设计
```

这部分会明显超出“会写 LangGraph API”的层级，进入一个有状态 LLM 系统真正上线要面对的问题。

## 正式写答案时的统一结构

每条主链建议形成一个独立深度章节，不限制篇幅，但禁止再写成浅显概念列表。

```text
1. 面试主问题
2. 先给 30～60 秒可直接回答的主答案
3. 这道题为什么会被问
4. 完整系统位置图
5. 机制原理
6. 用固定采购经营 Agent 跑一遍真实例子
7. State / 数据 / 外部系统在每一步分别是什么
8. 关键代码或伪代码
9. 原始候选题逐个作为追问展开
10. 生产故障与边界
11. 如何验证、监控或测试
12. 当前官方版本核验
```

## 不建议做的事情

- 不再单独花一章重新解释“State 是什么”；应该在 M04、M05、M07、M09 等不同问题里看到 State 在不同工程情景下发挥作用。
- 不把 69 道题逐题写 69 份高度重复答案。
- 不为了“压缩”删除 Security、Schema Migration、Cancel 等公开频率较低但生产价值高的问题。
- 不把第三方旧 API 写法直接当当前标准答案。
- 不把所有问题都强行套在 LangGraph 自己身上；权限、幂等、队列、沙箱等有很大一部分属于应用和基础设施责任。

## 当前建议

正式开始写答案时，先从 **M01～M03** 做一小组，确认新的“深度章节”质量明显高于 Part 1～3，再继续批量展开。

原因：前三题最贴近真实项目面试开场，而且能快速检验新的讲解方式是否足够深。如果质量不满意，调整模板的成本也最低。
