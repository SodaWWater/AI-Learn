# 04｜工程案例 3：模型输出写到一半被截断，Runtime 怎么把它“接着写完”

> 本章讨论的不是 Context 输入太长，而是另一类完全不同的问题：
>
> **模型已经开始正常回答，但输出达到本次请求允许的最大 Token 数，被强制截断。**
>
> Claude Code 不会简单把错误立即扔给用户，而是先尝试自动恢复。

---

# 1. 先看一个真实开发场景

用户让 Agent：

> “把这个模块的 8 个接口都检查一遍，逐个修改，并总结每处改动。”

模型开始输出：

~~~text
1. login 接口……
2. logout 接口……
3. refreshToken 接口……
4. resetPassword 接口……
~~~

写到一半突然停止。

不是模型觉得任务完成了。

而是：

~~~text
本次输出达到 max_output_tokens
~~~

剩下的内容根本没有生成出来。

---

# 2. max_output_tokens 是什么

先解释这个词。

模型一次请求，不可能无限输出。

系统会给本次响应设置一个：

> 最大输出 Token 数。

Token 可以暂时理解成：

> 模型处理文字时使用的计量单位。

所以：

~~~text
max_output_tokens
~~~

就是：

> “这一轮最多允许模型输出多少 Token。”

如果模型还想继续说，但已经撞到上限：

~~~text
输出被截断
~~~

---

# 3. 最简单实现会怎么做

Demo 很可能：

~~~ts
const response = await callModel()

if (response.error === "max_output_tokens") {
  throw new Error("输出过长")
}
~~~

于是用户看到：

~~~text
Error: max output tokens exceeded
~~~

问题是：

> 这不一定是一个真正无法恢复的错误。

模型其实已经完成了很多工作，只是“一口气说不完”。

直接失败会浪费：

- 已经生成的内容；
- 前面 Tool 调用成果；
- 用户等待时间；
- 已经付出的 Token 成本。

---

# 4. Runtime 的第一层思路：先别急着把错误给用户

当前 query.ts 里有一个很关键的设计：

> 对可恢复的 max_output_tokens 错误，先暂时不向 SDK Caller 暴露。

为什么？

假设：

~~~text
模型触发 max_output_tokens
↓
Runtime 立刻把 Error yield 给外部
↓
桌面端 / SDK 看到 Error
↓
认为整个 Turn 已经失败
↓
停止监听
~~~

但 Runtime 内部其实还想：

~~~text
提高上限
↓
Retry
~~~

这时就出现：

> Runtime 还在救，但外面已经认为死了。

所以源码有“withhold”逻辑。

---

# 5. withhold 是什么

withhold 可以翻成：

> 暂扣 / 暂时不对外暴露。

它不是：

> 把错误吃掉。

而是：

> “先看看 Runtime 能不能恢复；如果恢复彻底失败，再把真正错误交给外层。”

流程：

~~~text
发现 max_output_tokens
↓
暂扣错误
↓
尝试 Recovery
├─ 成功 → 用户不需要看到中间错误
└─ 失败 → 再把错误真正返回
~~~

这是生产容错里很重要的思想：

> Recovery before surfacing error。

翻成人话：

> 能自己修好，就先修；只有修不好，才让用户承担错误。

---

# 6. 第一阶段恢复：提高这一轮的输出上限

当前源码存在一条受 Feature / Provider 条件控制的路径：

~~~text
第一次撞到当前输出上限
↓
如果允许 escalation
↓
把 maxOutputTokensOverride 提高到更大的值
↓
重新执行同一个请求
~~~

源码里称：

~~~text
max_output_tokens_escalate
~~~

escalate 可以翻成：

> 升档 / 提高额度。

学习上不要死记具体默认值。

你只要理解设计：

> 如果失败只是“这一轮额度太小”，可以先增大额度再重试同一个请求，而不是马上修改对话语义。

---

# 7. 为什么“提高上限后重试”比直接续写更干净

假设输出只是因为某个临时上限太小而被截断。

方案 A：

~~~text
保留半截回答
↓
再告诉模型“接着写”
~~~

可能造成：

- 接续位置不自然；
- 模型重复内容；
- 多一次消息往返；
- 对话历史变复杂。

方案 B：

~~~text
提高输出额度
↓
同一个请求重新生成完整响应
~~~

如果能成功，消息轨迹更干净。

所以 Runtime 优先尝试这种“同请求重试”。

---

# 8. 但如果升档以后还是截断呢

这说明任务确实太长。

再无限提高上限并不现实。

这时 Claude Code 使用第二种恢复：

> 把已经输出的 Assistant 内容保留下来，再加入一条内部恢复消息，让模型从断点继续。

源码创建的恢复消息核心意思是：

~~~text
上一次输出达到限制。
直接继续，不要道歉，不要重新总结。
如果是在半个思路中断，就从那里接着做。
把剩余工作拆成更小的部分。
~~~

然后进入下一轮 queryLoop。

---

# 9. nudge 是什么

这时可以引入小林文章里的词：

**nudge（轻推）**：

> Runtime 不直接替模型完成任务，而是给模型加入一条内部提示，引导它下一轮继续正确行为。

它和普通用户消息不同。

这是 Runtime 自己生成的 Meta Message。

Meta 可以理解成：

> 给模型看的“运行控制提示”，不是用户真正输入的新要求。

所以新的消息可能变成：

~~~text
User:
完成 8 个接口的检查和修改

Assistant:
已经完成前 4 个……
[输出被截断]

Runtime Meta Message:
上次输出达到限制，直接从断点继续……
~~~

下一次模型看到这些，就知道：

> 不要重头再来，接着完成剩余任务。

---

# 10. 修复前后 messages 怎么变化

## 10.1 如果直接失败

~~~text
[
  User(Task),
  Assistant(半截输出)
]

Terminal:
max_output_tokens error
~~~

用户只能手动说：

~~~text
继续
~~~

---

## 10.2 Runtime 自动恢复

~~~text
[
  User(Task),

  Assistant(
    前半部分输出
  ),

  User(
    isMeta=true,
    "Output token limit hit. Resume directly..."
  )
]
~~~

然后：

~~~text
continue
↓
callModel()
~~~

模型再生成后半部分。

---

# 11. 为什么恢复消息特别强调“不要道歉、不要回顾”

如果只写：

~~~text
请继续
~~~

模型可能：

~~~text
抱歉刚才回答被截断了。
前面我们已经……
让我重新总结一下……
~~~

这会：

- 浪费更多输出 Token；
- 重复已经存在的内容；
- 让续写更容易再次超限。

所以 Runtime 的恢复提示非常具体：

> 直接续，不道歉，不 recap，把剩余工作拆小。

这不是 Prompt Engineering 炫技。

它是：

> Runtime 为了让恢复路径尽可能短、稳定、节省 Token 而设计的控制指令。

---

# 12. 这里为什么必须有 Recovery Count

现在回到上一章的 State。

假设：

~~~text
输出截断
↓
nudge
↓
继续
↓
又截断
↓
nudge
↓
继续
↓
又截断
↓
...
~~~

如果不限制：

> Recovery 自己变成无限循环。

所以 State 里有：

~~~text
maxOutputTokensRecoveryCount
~~~

当前源码常量：

~~~text
MAX_OUTPUT_TOKENS_RECOVERY_LIMIT = 3
~~~

意思：

> 多轮续写恢复最多尝试有限次数。

每次：

~~~text
count + 1
~~~

同时 transition 记录：

~~~text
reason = max_output_tokens_recovery
attempt = 当前第几次
~~~

---

# 13. 为什么 3 次之后必须“承认失败”

这里体现生产系统一个很重要的原则：

> 自动化系统必须有“放弃条件”。

不是：

~~~text
只要理论上可能成功
就永远继续
~~~

而是：

~~~text
恢复成功概率
vs
继续消耗的成本
~~~

达到某个边界后：

~~~text
停止自动恢复
↓
把之前暂扣的真实错误暴露出去
~~~

用户至少得到一个明确结果：

> 这次自动恢复耗尽，而不是 Agent 永远卡住。

---

# 14. 这个案例里其实有三种不同的“继续”

不要把所有 continue 当成同一种。

## 14.1 escalate 后的 continue

~~~text
请求语义不变
只提高输出上限
↓
重新跑同一请求
~~~

## 14.2 recovery nudge 后的 continue

~~~text
保留已经输出的内容
增加 Meta Message
↓
开启下一次模型生成
~~~

## 14.3 正常 Tool Result 后的 continue

~~~text
模型要 Tool
↓
执行 Tool
↓
把 Observation 放回
↓
继续
~~~

所以 transition.reason 很有用。

它告诉 Runtime：

> 这次 continue 到底属于哪一种。

---

# 15. 为什么 API Error 不能继续跑普通 Stop Hook

当前源码还有一个很值得学的保护。

假设：

~~~text
模型 API 本身报错
↓
Stop Hook 又判断“任务没完成”
↓
阻止结束并要求继续
↓
再次 API Error
↓
Stop Hook 再要求继续
↓
...
~~~

会形成新的死循环。

所以当前源码会判断：

~~~text
lastMessage.isApiErrorMessage
~~~

如果是真正 API Error：

> 不进入普通“模型回答后的 Stop Hook 评估”，而是直接走失败处理。

原因很简单：

> 模型根本没有产生一个有效回答，Stop Hook 没有正常业务结果可以评估。

这叫区分：

~~~text
业务结果不满意
vs
底层模型请求根本失败
~~~

两者不能走同一套控制逻辑。

---

# 16. Terminal Reason 是什么

Terminal 可以翻成：

> 终止状态。

Reason 就是：

> 为什么终止。

生产 Runtime 不应该最后只有：

~~~text
success = false
~~~

而应该：

~~~text
为什么失败？
~~~

例如：

~~~text
model_error
prompt_too_long
aborted_streaming
aborted_tools
max_turns
...
~~~

这样上层 UI / SDK 才知道：

- 是否应该提示用户重试；
- 是否是用户主动中断；
- 是否是资源限制；
- 是否是模型服务错误。

---

# 17. 一个完整时序

~~~mermaid
flowchart TD
    A["模型正常生成"] --> B{"达到 max_output_tokens?"}
    B -->|No| OK["正常继续"]
    B -->|Yes| W["暂扣错误，不立刻对外暴露"]

    W --> E{"允许输出额度升档?"}
    E -->|Yes| U["提高 maxOutputTokensOverride"]
    U --> R1["Retry 同一请求"]
    R1 --> B

    E -->|No / 升档后仍失败| C{"RecoveryCount < Limit?"}
    C -->|Yes| N["加入内部续写 nudge"]
    N --> INC["RecoveryCount + 1"]
    INC --> R2["进入下一轮模型调用"]
    R2 --> B

    C -->|No| FAIL["恢复耗尽，真正暴露错误"]
~~~

---

# 18. 这个设计为什么叫 Graceful Recovery

Graceful 可以翻成：

> 尽量让用户少感知系统内部故障。

这里：

~~~text
模型输出截断
~~~

本来是内部实现限制。

如果 Runtime 能自动：

~~~text
升档
或
续写
~~~

用户最终拿到完整结果，就不必承担这个内部细节。

这就是：

> Graceful Recovery（平滑恢复 / 优雅恢复）。

注意：

> Graceful 不是“错误提示写得漂亮”。

真正的 Graceful 是：

> 能恢复的故障尽量自动恢复，恢复不了再明确失败。

---

# 19. 这套思想怎么迁移到自己的 Agent

以后遇到：

~~~text
长输出
长任务
多阶段报告
代码大范围修改
~~~

可以设计：

## 第一层：检测“回答是不是完整”

不要只看有没有文本。

要看 API 的结束原因。

## 第二层：区分“可以同请求重试”还是“应该续写”

例如：

~~~text
临时额度低
→ 同请求重试

任务本身太长
→ 分段续写
~~~

## 第三层：续写提示要减少重复

不要只写：

~~~text
继续
~~~

要告诉模型：

- 从断点续；
- 不 recap；
- 剩余任务拆小；
- 不重复已经完成部分。

## 第四层：限制恢复次数

一定要有：

~~~text
Recovery Count
~~~

# 21. 本章最终心智模型

请记住：

~~~text
模型输出截断
≠
任务一定失败
~~~

Claude Code 的思路是：

~~~text
先识别这是可恢复错误
↓
暂时不把错误暴露给外层
↓
优先尝试更干净的同请求升档重试
↓
仍然失败，则把已生成内容保留
↓
加入内部 nudge 让模型续写
↓
Recovery Count 控制次数
↓
耗尽后才真正失败
~~~

这里真正值得学的是：

> **生产 Runtime 不把“API 一次请求的失败”直接等价成“用户任务失败”，它会在两者之间加入一个有限、可追踪、可停止的恢复层。**
