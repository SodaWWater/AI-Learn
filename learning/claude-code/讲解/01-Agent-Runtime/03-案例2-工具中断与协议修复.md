# 03｜工程案例 2：Tool 中途挂掉，为什么整个 Conversation 不会一起报废

> 本章学习 Claude Code Runtime 里最值得理解的工程细节之一：
>
> **模型已经发出了 tool_use，但 Tool 没有成功产生 tool_result 时，Runtime 必须主动修复消息链。**
>
> 这不是“为了提示用户友好一点”，而是为了让下一轮模型请求仍然满足协议要求。

---

# 1. 从一个最典型的事故开始

假设用户说：

> “帮我读取 auth.ts，然后看看登录为什么 401。”

模型先返回：

~~~text
我先读取 auth.ts。
~~~

并且产生：

~~~json
{
  "type": "tool_use",
  "id": "tool_123",
  "name": "Read",
  "input": {
    "file_path": "src/auth.ts"
  }
}
~~~

Runtime 收到后开始执行 Read。

就在这时：

~~~text
用户按下 Ctrl+C
~~~

或者：

~~~text
网络断开
~~~

或者：

~~~text
Streaming Fallback 被触发
~~~

结果是：

> 模型已经正式说“我要调用这个 Tool”，但 Tool 没有正常完成。

---

# 2. 为什么这不是普通的“工具失败”

如果只是：

~~~text
Read 文件不存在
~~~

Runtime 完全可以正常返回：

~~~text
tool_result:
File not found
~~~

这虽然是失败结果，但协议是完整的。

真正麻烦的是：

~~~text
tool_use 已经进入消息历史
↓
tool_result 根本没产生
~~~

于是消息可能变成：

~~~text
User:
帮我看 auth.ts

Assistant:
我先读取文件
tool_use id=tool_123
~~~

然后结束。

这条消息链处于“半完成”状态。

---

# 3. tool_use 和 tool_result 到底是什么关系

先把两个专业词重新讲清楚。

## tool_use

> 模型提出“我要执行某个 Tool”的结构化动作请求。

它包含：

~~~text
Tool 名
参数
tool_use id
~~~

例如：

~~~text
id = tool_123
Tool = Read
file = auth.ts
~~~

## tool_result

> Runtime 真正执行 Tool 后，把结果作为 Observation 返回给模型。

例如：

~~~text
tool_result
tool_use_id = tool_123
content = 文件内容
~~~

关键在：

~~~text
tool_use.id
必须和
tool_result.tool_use_id
对应
~~~

可以把它理解成请求和回执：

~~~text
请求编号 A123
↓
必须有回执编号 A123
~~~

---

# 4. 为什么缺一个 tool_result 会让下一轮出问题

假设用户中断以后又说：

> “没事，继续。”

Runtime 如果直接拿旧 messages 再请求模型：

~~~text
User("帮我看 auth.ts")

Assistant(
  tool_use id=tool_123
)

User("继续")
~~~

中间少了：

~~~text
tool_result id=tool_123
~~~

这意味着：

> 上一次 Tool Call 在消息协议里没有闭合。

对 Tool Calling API 来说，这不是简单的业务失败，而可能是：

> 消息结构本身不合法。

所以最坏情况不是：

~~~text
模型说“读取失败”
~~~

而是：

~~~text
API 直接拒绝下一次请求
~~~

Conversation 从这一刻开始无法正常继续。

---

# 5. Demo 写法为什么很容易漏掉这个问题

简单实现往往是：

~~~ts
const toolResult = await runTool(toolUse)
messages.push(toolResult)
~~~

开发者默认：

~~~text
runTool()
要么成功 return
要么 throw
~~~

于是 catch 里可能：

~~~ts
catch (e) {
  return
}
~~~

问题就在这里：

> 代码退出了，但消息协议里的 tool_use 还留着。

也就是说：

~~~text
程序控制流结束了
≠
消息状态已经合法结束
~~~

这是本章最重要的一句话。

---

# 6. Claude Code 怎么修

当前源码里有一个很直接的函数：

~~~text
yieldMissingToolResultBlocks()
~~~

名字拆开：

~~~text
yield
= 产生并向外发送

Missing Tool Result Blocks
= 缺失的 Tool Result 块
~~~

它会扫描已经产生的 Assistant Messages。

如果发现里面有：

~~~text
tool_use id=A
~~~

但当前执行异常导致没有真实结果，就主动生成：

~~~json
{
  "type": "tool_result",
  "tool_use_id": "A",
  "is_error": true,
  "content": "工具因为某个错误没有完成"
}
~~~

这叫：

> Synthetic Tool Result。

---

# 7. Synthetic Tool Result 是什么

Synthetic 可以翻成：

> 人工合成的。

所以 Synthetic Tool Result 不是 Tool 真正成功执行出来的数据。

它表达的是：

> “这个 Tool 没有正常执行，但 Runtime 仍然补上一条正式结果，告诉模型它失败了。”

例如：

~~~text
tool_use:
Read auth.ts
id=A

↓

真实 Read 没完成

↓

Runtime 合成：

tool_result:
id=A
is_error=true
"Interrupted by user"
~~~

这样消息协议重新闭合。

---

# 8. 修复前后 messages 对比

## 8.1 修复前

~~~text
[
  User("读取 auth.ts"),

  Assistant(
    tool_use id=A
    Tool=Read
  )
]
~~~

状态：

~~~text
A 没有结果
~~~

下一轮风险：

~~~text
API 拒绝
~~~

---

## 8.2 修复后

~~~text
[
  User("读取 auth.ts"),

  Assistant(
    tool_use id=A
    Tool=Read
  ),

  User(
    tool_result id=A
    is_error=true
    "Interrupted by user"
  )
]
~~~

现在模型下一轮可以正常理解：

> 上一个动作失败了。

然后它可能：

- 再试一次；
- 换其他 Tool；
- 问用户；
- 直接解释当前无法继续。

这叫：

> 把 Runtime 异常重新变成模型可以理解的 Observation。

---

# 9. 这套问题不只发生在 Ctrl+C

这是这个案例真正高价值的地方。

看起来我们只解决：

~~~text
用户中断 Tool
~~~

但实际上很多故障都会产生同一个底层问题：

> Tool Use 已经产生，但对应结果可能永远回不来。

---

## 9.1 模型 Streaming 中途异常

可能：

~~~text
模型已经流出：
tool_use A
↓
后面的 Streaming 报错
~~~

如果 Runtime 直接退出：

~~~text
A 没有 result
~~~

所以异常处理路径也要补齐。

---

## 9.2 Runtime 自己抛异常

例如：

~~~text
模型已经产生 tool_use
↓
Runtime 某个内部 Bug throw
↓
Tool 没跑完
~~~

源码外层 catch 会尽量：

~~~text
yieldMissingToolResultBlocks(...)
~~~

然后再把真正 Runtime Error 往外暴露。

---

## 9.3 Model Fallback

Fallback 先解释成人话：

> 主模型这一轮执行失败后，切换到备用模型重新完成这次请求。

问题是：

~~~text
Model A
已经产生 tool_use A1

↓
中途需要切换 Model B

↓
A1 对应的 Tool 可能已经开始，甚至半完成
~~~

如果直接让 Model B 接手：

~~~text
A 的半截 Assistant
A 的 tool_use
旧 Tool Result
B 的新输出
~~~

可能混在一起。

于是 Runtime 需要：

~~~text
清空失败 attempt 的 assistantMessages
清空 toolResults
清空 toolUseBlocks
丢弃旧 StreamingToolExecutor
重新创建 Executor
~~~

这里的核心不是“切模型”。

而是：

> **切换执行尝试时，必须清理上一尝试产生的半成品。**

---

# 10. 什么叫 Orphan

源码和工程里经常会出现：

> orphan message / orphan tool result

Orphan 就是：

> 孤儿。

例如：

~~~text
tool_result id=A
~~~

但新的消息历史里已经没有：

~~~text
tool_use id=A
~~~

那这条 Tool Result 就成了“孤儿结果”。

反过来：

~~~text
tool_use id=A
~~~

没有 Tool Result，也可以理解成“未闭合调用”。

生产 Runtime 必须避免：

~~~text
孤儿 tool_use
孤儿 tool_result
~~~

---

# 11. 为什么 Fallback 时要 discard StreamingToolExecutor

假设：

~~~text
Model A:
tool_use A

StreamingToolExecutor 已经开始执行 A

↓
模型请求触发 Fallback

Model B:
重新生成一套新的 Tool Call
~~~

如果旧 Executor 继续跑：

~~~text
A 最后返回 tool_result
~~~

但现在 Runtime 已经在处理 Model B 的新消息。

于是会出现：

~~~text
旧 Tool Result
插进新模型轨迹
~~~

这种结果会污染新请求。

所以源码在 Fallback 时：

~~~text
streamingToolExecutor.discard()
~~~

然后新建一个新的 Executor。

discard 可以先理解成：

> 明确宣布“上一轮执行器产生的结果全部作废，不再进入当前消息链”。

---

# 12. Abort 又是什么

Abort 不要先理解成某个类。

先理解需求：

> 用户说“停”，Runtime 要把正在进行的异步工作尽快取消。

这叫：

> Abort（中止）。

Claude Code 里用 AbortController / AbortSignal 把这个“停止信号”传给：

- Model Streaming；
- Tool；
- Bash 子进程；
- 其他异步操作。

但是：

> Abort 只负责“停下来”，并不自动修好消息协议。

所以 Abort 后还需要：

~~~text
补 synthetic tool_result
清理执行器
返回明确的 terminal reason
~~~

这就是为什么：

~~~text
Abort
≠
简单 return
~~~

---

# 13. 为什么源码区分 aborted_streaming 和 aborted_tools

用户都是按 Ctrl+C。

为什么 Runtime 还要分？

因为中断位置不同，清理工作不同。

## aborted_streaming

发生时：

~~~text
模型还在流式输出
~~~

可能需要：

- 停模型请求；
- 检查已经出现哪些 tool_use；
- 为未闭合 Tool Call 补结果；
- 清理 Streaming Tool Executor。

## aborted_tools

发生时：

~~~text
模型已经流完
Tool 正在执行
~~~

可能需要：

- 中断正在执行 Tool；
- 处理已完成 Tool；
- 处理未开始 Tool；
- 补对应的 synthetic result。

所以：

> 同样是“用户取消”，Runtime 也必须知道事故发生在哪个阶段。

---

# 14. StreamingToolExecutor 自己也会制造 synthetic error

当前源码的 StreamingToolExecutor 里专门有：

~~~text
createSyntheticErrorMessage()
~~~

它处理例如：

~~~text
user_interrupted
streaming_fallback
sibling_error
~~~

### user_interrupted

用户取消 Tool。

会产生错误 Tool Result，让协议闭合。

### streaming_fallback

Streaming Fallback 后，旧 Tool 执行结果已经不应该继续使用。

会明确返回：

~~~text
这个 Tool 因 Streaming Fallback 被丢弃
~~~

### sibling_error

多个 Tool 并行时，如果某些 Tool 发生会影响兄弟任务的错误，其他 Tool 可能被取消，也要各自得到错误结果。

这里再次体现：

> 取消执行和修复消息协议是同时存在的两条工作。

---

# 15. 为什么“错误 Tool Result”比直接 throw 更有价值

假设 Tool 失败。

方案 A：

~~~text
throw Error
↓
整个 Agent Turn 结束
~~~

方案 B：

~~~text
生成 tool_result:
is_error=true
↓
模型看到失败原因
↓
模型自己决定下一步
~~~

方案 B 更符合 Agent 思想。

因为对于模型来说：

~~~text
成功的 Tool Result
是 Observation

失败的 Tool Result
同样是 Observation
~~~

例如：

~~~text
Read auth.ts:
File not found
~~~

模型可以判断：

~~~text
那我先 Glob 找文件。
~~~

所以：

> Tool Error 不一定等于 Runtime Error。

这是一个非常重要的边界。

---

# 16. 哪些错误应该给模型，哪些应该终止 Runtime

可以先粗略分：

## 可作为 Observation 的错误

例如：

~~~text
文件不存在
Grep 没结果
某个命令返回非 0
某个网络资源没找到
~~~

模型还能基于结果继续决策。

适合：

~~~text
tool_result is_error=true
↓
让模型继续
~~~

## Runtime 本身无法维持正确性的错误

例如：

~~~text
内部状态损坏
模型 API 无法工作
消息协议无法恢复
资源已经被强制终止
~~~

可能需要：

~~~text
terminal reason
↓
结束 User Turn
~~~

生产 Agent 不能把所有 Error 都统一 throw，也不能所有 Error 都塞给模型。

# 17. 一个更完整的事故时序

~~~mermaid
sequenceDiagram
    participant U as User
    participant L as LLM
    participant R as Runtime
    participant T as Tool

    U->>R: 帮我读 auth.ts
    R->>L: Messages + Tools
    L-->>R: tool_use id=A, Read(auth.ts)
    R->>T: 开始执行 Read

    U->>R: Ctrl+C
    R->>T: Abort

    Note over R: 发现 A 没有正常 tool_result

    R->>R: 生成 synthetic tool_result id=A
    R-->>U: Turn 被中断

    U->>R: 继续
    R->>L: 完整合法的 Message History
    L-->>R: 继续决策
~~~

核心是：

> 第二次请求能成功，不只是因为 Tool 停了，而是因为上一轮消息链被修好了。

---

# 18. 这背后的通用工程思想：Protocol Invariant

现在引入一个稍微专业的词。

Invariant 可以翻成：

> 始终必须成立的规则。

Tool Calling 的一个重要规则就是：

~~~text
每一个进入消息链的 tool_use
都必须有一个对应的 tool_result
~~~

这叫：

> Protocol Invariant（协议不变量）。

生产 Runtime 的责任之一就是：

> 无论正常、异常、中断还是 Fallback，都尽量维持这个规则成立。

所以你以后写 Agent，不应该只问：

~~~text
错误时怎么退出？
~~~

还应该问：

~~~text
错误退出以后，系统状态还满足下一次执行的协议要求吗？
~~~

---

# 19. Compensation：为什么 synthetic result 可以看成补偿动作

再引入一个常见工程思想。

Compensation 可以翻成：

> 补偿。

意思是：

> 前一个动作只完成了一半时，用另外一个动作把系统恢复到一个可继续工作的状态。

这里：

~~~text
tool_use 已经产生
但 Tool 没正常完成
~~~

无法把历史时间倒回去。

所以 Runtime 不能删除“模型曾经调用 Tool”这个事实。

它只能补：

~~~text
一个明确失败的 tool_result
~~~

让协议闭合。

这就是一种补偿式恢复。

# 20. 以后自己写 Agent 时应该检查什么

看到 Tool Calling Runtime，至少问以下问题：

## 20.1 Tool Call 有没有唯一 ID

没有 ID 很难可靠匹配 Result。

## 20.2 Tool 失败是否仍然产生 Result

最好让错误也变成结构化 Observation。

## 20.3 中断发生在 Tool Use 后怎么办

不能只 cancel Promise。

还要处理消息状态。

## 20.4 Retry / Fallback 是否会混入旧 Tool Result

需要明确：

~~~text
哪些结果保留
哪些结果作废
~~~

## 20.5 并行 Tool 中一个失败，兄弟 Tool 怎么办

后面 StreamingToolExecutor 章节会继续讲。

# 22. 本章最终心智模型

请把下面这条链记住：

~~~text
Model:
tool_use id=A
↓
Runtime 开始 Tool
↓
中途异常
↓
不能只 return / throw
↓
先保证：
tool_result id=A
is_error=true
↓
消息协议重新闭合
↓
再决定继续还是结束
~~~

真正的生产级思想是：

> **Runtime 不只负责“让 Tool 执行”，还负责在 Tool 没有正常执行完时，把消息状态修复到下一轮仍然可用。**

> Tool 没坏，但模型自己的输出写到一半撞上 Token 上限，Runtime 怎么在用户几乎无感的情况下把它续回来？
