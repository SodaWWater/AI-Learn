# 01｜总体架构与正常主循环：先看清 Runtime 到底是什么

> 本章只做一件事：把 Claude Code Runtime 的“骨架”讲清楚。
>
> 如果这一章没有真正理解，后面的 State、Abort、Fallback、StreamingToolExecutor 都会变成零散名词。

---

## 1. 先纠正一个最容易混乱的认识

小林文章里说一句用户输入会经过四层：

<code>ask() → QueryEngine.submitMessage() → query() → queryLoop()</code>

这四层不是四个互相独立的系统模块，也不是四套并列架构。

它们首先是一条真实的函数调用链。

可以先把它想成四层套娃：

~~~text
ask(
  submitMessage(
    query(
      queryLoop()
    )
  )
)
~~~

最里面的 <code>queryLoop()</code> 才有真正反复执行的 <code>while (true)</code> Agent Loop。

所以一个更准确的总体认识是：

> Runtime 的中心是 queryLoop 这个大循环，但大循环外面还包着入口、会话管理和生命周期管理。

---

## 2. 一张图先把四层放对位置

~~~mermaid
flowchart TB
    OUT["外部调用方<br/>CLI / SDK / REPL / Headless"]

    A["L1 ask()<br/>方便发起一次调用"]
    B["L2 QueryEngine.submitMessage()<br/>把用户输入准备成一次完整 Turn"]
    C["L3 query()<br/>给整次执行套上开始/结束生命周期"]
    D["L4 queryLoop()<br/>真正的 Agent Loop"]

    OUT --> A --> B --> C --> D

    subgraph LOOP["queryLoop 内部"]
      direction LR
      X1["准备本轮消息"] --> X2["调用模型"]
      X2 --> X3["解析模型输出"]
      X3 --> X4{"有 tool_use ?"}
      X4 -->|有| X5["执行 Tool"]
      X5 --> X6["得到 tool_result"]
      X6 --> X7["更新 messages / State"]
      X7 --> X1
      X4 -->|没有| X8["判断是否结束"]
    end

    D --> LOOP
~~~

这张图只表达调用关系，不表达 Context、Memory、Skill 等能力模块。

后者会“挂”到 queryLoop 的不同节点上，但不是这四层中的第五层、第六层。

---

# 3. 用一个真实任务贯穿整章

假设用户输入：

> “帮我看看这个项目的登录接口为什么一直返回 401，找到原因并告诉我怎么修。”

为了让例子清晰，假设 Claude Code 最终经历：

~~~text
用户问题
  ↓
模型决定先搜索登录代码
  ↓
Grep
  ↓
找到 auth.ts
  ↓
Read auth.ts
  ↓
模型发现 Bearer Token 处理错误
  ↓
最终回答
~~~

下面不先讲抽象概念，直接看这句话经过四层时，每一层拿到什么、干了什么、交给下一层什么。

---

# 4. 第一层 ask()：把“外部调用”接进 Runtime

## 4.1 进入 ask() 之前有什么

外部调用大致类似：

~~~ts
ask({
  prompt: "帮我看看登录接口为什么一直返回 401",
  cwd: "/project",
  tools: [...],
  mcpClients: [...],
  maxTurns: 20,
  fallbackModel: "...",
  ...
})
~~~

此时这些数据还是“调用参数”。

它们表达：

- 用户说了什么；
- 当前项目目录在哪；
- 允许 Runtime 使用哪些 Tool；
- 用哪个模型；
- 最多跑多少轮；
- 权限怎么判断；
- 中断控制器从哪里来。

你暂时不需要记这些参数名字。

只要理解：

> ask() 收到的是“我要启动一次 Claude Code 执行”所需的外部配置。

---

## 4.2 ask() 真正做什么

当前源码里的注释把它定义为：

> Convenience wrapper around QueryEngine for one-shot usage.

翻成人话：

> 一个方便别人“一次性调用 Claude Code”的包装函数。

它的核心行为可以压缩成：

~~~ts
const engine = new QueryEngine(config)

yield* engine.submitMessage(prompt)
~~~

所以 ask() 本身并不负责：

- 分析 401；
- 调模型；
- 执行 Grep；
- 管理 Agent Loop。

它主要负责：

1. 创建一个 QueryEngine；
2. 把 prompt 交给 QueryEngine；
3. 把内部持续产出的事件继续往外传。

---

## 4.3 这一层的数据变化

进入：

~~~text
prompt + 各类调用配置
~~~

出来：

~~~text
QueryEngine 实例
+
把 prompt 交给 submitMessage()
~~~

也就是说：

> ask() 不是主要的数据加工层，它更像“启动入口”。

---

# 5. 第二层 QueryEngine.submitMessage()：把一句话变成一次可执行的 User Turn

这一层比 ask() 重要得多。

它真正解决的问题是：

> “用户刚发来的这句话，怎样接入当前 Conversation，并准备成一次可以交给 Agent Loop 执行的任务？”

---

## 5.1 先理解 QueryEngine 是什么

源码里明确写着：

> One QueryEngine per conversation.

即：

> 一个 Conversation 对应一个 QueryEngine。

Conversation 可以先翻成：

> 你现在打开的这一整个持续会话。

比如：

~~~text
User: 这是一个 Node.js 项目
Assistant: 好的

User: 登录接口在 auth 模块
Assistant: 明白

User: 帮我看看为什么一直 401
~~~

这些不是三个独立任务世界。

它们属于同一个 Conversation。

QueryEngine 会持有一些会跨用户输入继续存在的数据，例如：

- 历史消息；
- 文件读取状态；
- 使用量；
- 权限拒绝记录；
- AbortController；
- 一些 Memory / Skill 的会话级记录。

所以可以把 QueryEngine 理解成：

> “当前对话窗口背后的 Runtime 记账本 + 控制器”。

---

## 5.2 submitMessage() 对应什么

每次用户再输入一句：

~~~text
帮我看看登录为什么 401
~~~

就是一次新的 User Turn。

Turn 可以翻成：

> 用户发起一次新任务，到这次任务结束之间的整个过程。

注意：

一个 User Turn 内部可以调用很多次模型和 Tool。

所以：

~~~text
User Turn
≠
一次模型请求
~~~

---

## 5.3 submitMessage() 第一步：准备当前 Turn 的运行材料

它会拿到或建立：

~~~text
当前历史 messages
System Prompt
userContext
systemContext
Tool 列表
Model
Permission 状态
AbortController
Budget
...
~~~

专业词先不用死记。

这里你只需要把它理解成：

> “要让 Agent 真正开始工作，除了用户一句话，还得把当前会话历史、项目环境、工具、权限和模型设置一起准备好。”

---

## 5.4 submitMessage() 第二步：processUserInput()

用户输入不是直接扔给模型。

因为输入可能是：

~~~text
普通问题
/compact
/reload-plugins
某个本地命令
特殊控制命令
~~~

所以先过 <code>processUserInput()</code>。

原来：

~~~text
"帮我看看登录接口为什么一直返回 401"
~~~

会被转换成内部 Message。

简化后：

~~~json
{
  "type": "user",
  "message": {
    "role": "user",
    "content": "帮我看看登录接口为什么一直返回 401"
  }
}
~~~

同时 <code>processUserInput()</code> 还会告诉 Runtime：

~~~text
shouldQuery = true / false
allowedTools = ...
model = ...
~~~

### shouldQuery 是什么

就是：

> 这次输入是否真的需要进入大模型 Agent Loop。

例如某个纯本地命令：

~~~text
shouldQuery = false
~~~

那么就不必浪费一次模型请求。

这是一层输入路由。

---

## 5.5 submitMessage() 第三步：把新消息加入 Conversation

假设之前：

~~~text
messages = [
  User("这是 Node.js 项目"),
  Assistant("好的")
]
~~~

新消息进入后：

~~~text
messages = [
  User("这是 Node.js 项目"),
  Assistant("好的"),
  User("帮我看看登录为什么 401")
]
~~~

此时用户的原始 String 已经变成：

> Conversation 里的正式 Message。

---

## 5.6 submitMessage() 第四步：为什么要先保存 Transcript

Transcript 可以先翻成：

> 会话执行记录文件。

当前源码会在真正进入 query loop 前，先把用户消息记录下来。

为什么？

假设：

~~~text
用户发出问题
↓
消息只在内存
↓
模型 API 正在请求
↓
进程突然被 kill
~~~

如果之前没落盘：

~~~text
重新启动
↓
resume
↓
找不到用户刚才那条消息
~~~

所以源码选择：

~~~text
接收消息
↓
先 recordTranscript
↓
再进入 query()
~~~

这里背后的工程思想是：

> 开始不可预测的长任务之前，先把关键恢复点保存下来。

现在先记住用途即可，后面 Session / Persistence 再细学。

---

## 5.7 submitMessage() 最终交给 query() 的东西

到了这里，已经不再只有一句 prompt。

而是接近：

~~~text
messages
systemPrompt
userContext
systemContext
toolUseContext
fallbackModel
maxTurns
taskBudget
...
~~~

这里出现一个词：<code>toolUseContext</code>。

先不要把它和 LLM 的 Context Window 混在一起。

它不是“发给模型看的上下文”。

它更接近：

> Runtime 执行 Tool 时需要的一包程序运行信息。

里面会有：

- Tools；
- AbortController；
- AppState 的读取/更新方法；
- 文件读取状态；
- 当前 Agent ID；
- Permission 等能力。

后面 Tool 专题再详细讲。

---

# 6. 第三层 query()：它为什么最容易让人困惑

你前面最难理解的就是这一层，因为它不像 submitMessage() 和 queryLoop() 那样“看起来干了很多活”。

先给结论：

> query() 不是主要业务处理层，也不是消息大幅转换层。它的核心价值是“给整次 Agent 执行建立生命周期边界”。

---

## 6.1 什么叫“生命周期边界”

假设你启动一项长任务。

它会经历：

~~~text
任务开始
↓
任务正在执行
↓
任务正常结束 / 中断 / 报错
↓
无论哪一种都要做收尾
~~~

Runtime 必须保证：

- 成功时清理；
- 失败时也清理；
- 用户中断时也清理；
- 异常 throw 时同样清理。

所以源码形态大致是：

~~~ts
try {
  terminal = yield* queryLoop(...)
} catch (error) {
  记录这是异常退出
  throw error
} finally {
  无论成功失败都执行收尾
}
~~~

这里最重要的是 finally。

finally 的意思是：

> 前面无论正常 return、抛异常还是中断，最终都必须执行这里的清理逻辑。

---

## 6.2 query() 具体收尾什么

当前源码里能看到：

- 结束或刷新 trace；
- finalize 当前 Turn 消费过的命令；
- 清掉 trace 相关引用；
- 清 Performance buffer；
- 通知一些命令生命周期完成。

这些名字现在都不用背。

只需要理解共同点：

> 它们不是 Agent“怎么解决 401”的业务逻辑，而是“一次 Runtime 执行结束后必须收拾的系统现场”。

---

## 6.3 为什么不直接 submitMessage() → queryLoop()

可以，Demo 里完全可以这么写。

但这样 queryLoop 会逐渐承担：

~~~text
怎么循环
怎么调模型
怎么执行 Tool
怎么恢复
怎么记录 trace
怎么结束 trace
怎么释放资源
怎么清 buffer
怎么通知外围系统
~~~

最终核心循环会越来越难维护。

所以拆成：

~~~text
query()
负责整趟执行的外壳和收尾

queryLoop()
负责内部怎么一圈圈运行
~~~

这是职责分离。

职责分离的意思：

> 一段代码尽量只对一种问题负责。

---

## 6.4 一个生活例子

把 queryLoop 想成正在做手术的医生：

~~~text
观察
↓
操作
↓
再观察
↓
继续操作
↓
完成
~~~

query() 更像手术室的整套流程：

~~~text
登记手术开始
↓
让医生真正做手术
↓
无论成功、异常还是中断
↓
结束记录
清理现场
释放资源
~~~

医生不应该一边手术，一边负责所有医院级收尾工作。

这就是 query() 的意义。

---

# 7. 第四层 queryLoop()：真正的 Agent 心脏

到了这里才进入：

~~~text
while (true)
~~~

它每一轮做的事情，先压缩成五步：

~~~text
1. 准备这一轮给模型看的消息
2. 流式调用模型
3. 判断模型有没有要求 Tool
4. 有 Tool 就执行
5. 把 Tool Result 加回去，进入下一轮
~~~

---

# 8. 先理解三个时间尺度

在继续 Happy Path 前，一定区分：

## Conversation

整个持续会话。

~~~text
QueryEngine 生命周期
~~~

## User Turn

用户新发一句任务，到这一任务结束。

~~~text
submitMessage()
~~~

## Loop Iteration

User Turn 内部，因为 Tool 调用而产生的一次模型往返。

例如：

~~~text
Iteration 1:
Model → Grep

Iteration 2:
Model → Read

Iteration 3:
Model → Final Answer
~~~

所以：

~~~text
一个 Conversation
包含很多 User Turn

一个 User Turn
又可能包含很多 Loop Iteration
~~~

---

# 9. Happy Path：一轮到底怎么转起来

继续用登录 401。

初始 messages：

~~~text
[
  User("帮我看看登录为什么 401")
]
~~~

---

## 9.1 Iteration 1：模型决定先搜索

queryLoop 准备本轮的 <code>messagesForQuery</code>。

这个词翻成人话：

> 这一轮真正准备发给模型的消息版本。

为什么不直接叫 messages？

因为历史 messages 后面可能经过：

- Tool Result 缩减；
- Snip；
- Compact；
- Context Collapse 等处理。

所以：

~~~text
messages
=
Runtime 手里保留的历史

messagesForQuery
=
这一轮处理后真正给模型看的版本
~~~

在这个短例子里暂时近似相同。

模型得到：

~~~text
System Prompt
+
项目环境
+
User("帮我看看登录为什么 401")
+
Tools 的描述
~~~

然后输出：

~~~text
我先搜索登录相关代码。
~~~

同时给出一个结构化 Tool 请求：

~~~json
{
  "type": "tool_use",
  "id": "tool_001",
  "name": "Grep",
  "input": {
    "pattern": "login|401|Unauthorized"
  }
}
~~~

### tool_use 是什么

只记一句：

> 模型没有权限自己执行程序，它只能发一个“我想调用某工具”的结构化请求，这个请求叫 tool_use。

---

## 9.2 queryLoop 怎么判断要不要继续

源码不会做复杂“意图识别”。

它主要观察：

> 这一轮模型输出里有没有真正出现 tool_use block。

如果出现：

~~~text
needsFollowUp = true
~~~

翻成人话：

> 现在还不能结束，因为模型还要求做一个动作。

---

## 9.3 执行 Grep

Runtime 找到 Grep Tool。

实际执行前还可能经过 Permission。

Permission 可以先翻成：

> Runtime 判断“模型提出的动作到底允不允许真的执行”。

模型只是提出请求，最终执行权在 Runtime。

Grep 得到：

~~~text
src/controllers/LoginController.ts
src/middleware/auth.ts
src/services/AuthService.ts
~~~

Runtime 把它包装成：

~~~json
{
  "type": "tool_result",
  "tool_use_id": "tool_001",
  "content": "src/controllers/LoginController.ts ..."
}
~~~

### tool_result 是什么

就是：

> Tool 实际执行后的 Observation，也就是模型下一轮要看到的结果。

---

## 9.4 第一轮结束时，messages 怎么变

原来：

~~~text
[
  User("帮我看看登录为什么 401")
]
~~~

现在：

~~~text
[
  User("帮我看看登录为什么 401"),

  Assistant(
    "我先搜索登录代码",
    tool_use id=tool_001 Grep(...)
  ),

  User(
    tool_result id=tool_001:
    "LoginController.ts, auth.ts..."
  )
]
~~~

这里非常关键：

> Agent Loop 的本质，就是不断把“模型动作”和“动作结果”追加到下一轮可见历史里。

---

## 9.5 Iteration 2：模型根据 Grep 结果继续

模型现在知道有：

~~~text
auth.ts
~~~

于是输出：

~~~text
我要看看 auth.ts。
~~~

并产生：

~~~text
tool_use id=tool_002
Tool = Read
file = auth.ts
~~~

Read 返回：

~~~ts
const auth = req.headers.authorization
const token = auth.replace("Bearer", "")
~~~

于是历史继续增长：

~~~text
User(question)

Assistant(tool_use Grep)
User(tool_result Grep)

Assistant(tool_use Read)
User(tool_result Read)
~~~

---

## 9.6 Iteration 3：模型已经有足够证据

模型看到：

~~~ts
"Bearer abc"
.replace("Bearer", "")
~~~

结果可能变成：

~~~text
" abc"
~~~

前面残留一个空格，后续 Token 校验可能失败。

于是模型直接输出最终回答，不再产生 tool_use。

此时：

~~~text
needsFollowUp = false
~~~

Runtime 就进入“是否真正结束”的检查。

正常情况下最终：

~~~text
return { reason: "completed" }
~~~

---

# 10. 为什么说“queryLoop 是循环发动机，外围是保护系统”

正常 Happy Path 其实很短：

~~~mermaid
flowchart LR
    A["准备消息"] --> B["Model"]
    B --> C{"tool_use?"}
    C -->|Yes| D["Tool"]
    D --> E["tool_result"]
    E --> A
    C -->|No| F["完成"]
~~~

如果只写 Demo，几十行就可以。

真正让 query.ts 很长的是：

- Tool 中断了怎么办；
- 模型输出截断怎么办；
- Retry 怎么防无限循环；
- Context 太长怎么办；
- Streaming 中途 Fallback 怎么清半成品；
- 多 Tool 怎么并发又不互相破坏；
- 用户 Ctrl+C 时消息协议怎么保持合法。

这些才是后面四个工程案例的重点。

---

# 11. 四层之间的数据到底怎么变化

把前面再压成一张表。

| 层 | 进入时 | 主要做什么 | 交给下一层 |
|---|---|---|---|
| ask() | prompt + 外部配置 | 创建 QueryEngine，启动一次调用 | prompt + Conversation Runtime |
| submitMessage() | 用户输入 + Conversation State | 输入处理、加入 messages、准备 System/Tool/Model、先持久化用户消息 | 一次已经准备好的 User Turn |
| query() | 完整 Turn 参数 | 套生命周期，负责外围开始/收尾 | 基本原样交给 queryLoop |
| queryLoop() | messages + Runtime 能力 | 反复 Model ↔ Tool，持续修改 messages / State | Terminal Reason + 持续事件 |

最值得记住的是：

> 前三层主要是“逐步建立运行边界”；真正高频改变消息和执行状态的是 queryLoop。

因此不要强行寻找：

~~~text
query() 把数据 A 转成了什么完全不同的数据 B
~~~

因为它本来就不是主要数据变换层。

---

# 12. 四层还有第二条方向：事件从里向外流

控制调用是：

~~~text
ask
→ submitMessage
→ query
→ queryLoop
~~~

但执行事件会反向流出：

~~~text
queryLoop
→ query
→ submitMessage
→ ask / SDK Caller
~~~

例如 queryLoop 可能产生：

~~~text
Assistant Text
Tool Progress
Tool Result
Attachment
Compact Boundary
...
~~~

这些事件通过 async generator 一层层被外部实时消费。

---

# 13. 什么是 async generator

普通 async 函数像：

~~~text
开始任务
↓
等 30 秒
↓
最后一次性 return
~~~

async generator 像：

~~~text
开始任务
↓
有一点结果就 yield
↓
继续干
↓
又有一点结果就 yield
↓
继续干
~~~

所以用户能实时看到：

- 模型文字逐步出现；
- Tool Progress；
- 中间事件。

<code>yield*</code> 可以理解成：

> “把里面那个 generator 产生的事件继续原样往外转发。”

所以：

~~~ts
terminal = yield* queryLoop(...)
~~~

不是“等 queryLoop 全做完再一次性拿结果”。

而是：

> queryLoop 运行过程中 yield 出来的事件，会持续穿过 query()。

# 14. 为什么这套架构值得学

到这里先不要背函数。

真正值得带走的是四个设计思想。

## 14.1 Conversation State 和 Agent Loop 分开

QueryEngine 管长期会话。

queryLoop 管一个 Turn 内的执行循环。

这样不会把所有状态堆进 while(true)。

## 14.2 核心 Loop 和外围生命周期分开

query() 负责“开始/结束/清理”。

queryLoop 负责“怎么继续执行”。

## 14.3 LLM 只做决策，不直接执行动作

模型产出 tool_use。

Runtime 决定是否允许并真正运行 Tool。

## 14.4 Agent 的 Observation 重新进入下一轮

Tool Result 不是终点。

它会被加入消息历史，让模型下一轮基于真实执行结果继续判断。

这就是 ReAct 类 Agent 最核心的运行闭环。
