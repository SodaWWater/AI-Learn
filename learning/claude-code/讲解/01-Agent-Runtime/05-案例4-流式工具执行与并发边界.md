# 05｜工程案例 4：模型还没说完，Tool 为什么已经开始跑？并发又为什么不能全开

> 本章解决两个看似矛盾的问题：
>
> 1. Agent 为什么要尽早执行 Tool，减少等待时间？
> 2. 为什么又不能把所有 Tool 一股脑并发执行？
>
> Claude Code 的核心答案是 StreamingToolExecutor：一边接收模型流，一边尽早启动“确认并发安全”的 Tool；不安全的 Tool 必须独占。

---

# 1. 先看最朴素的 Agent 为什么慢

假设模型这一轮想做三件事：

~~~text
Read A.ts
Read B.ts
Grep "login"
~~~

最简单实现：

~~~text
先等模型完整输出完
↓
收齐三个 tool_use
↓
执行 Read A
↓
执行 Read B
↓
执行 Grep
↓
把三个结果交给模型
~~~

假设：

~~~text
模型 Streaming 用 5 秒
每个 Tool 各用 2 秒
~~~

完全串行时：

~~~text
5 + 2 + 2 + 2
≈ 11 秒
~~~

很多时间都在互相等。

---

# 2. 为什么 Streaming 给了一个优化机会

模型不是一次性把整段响应返回。

它会逐步流出：

~~~text
文字……
tool_use A
文字……
tool_use B
文字……
tool_use C
~~~

当第一个完整 tool_use 已经出现时，Runtime 其实已经知道：

~~~text
Tool 名
Tool 参数
Tool ID
~~~

那为什么还要等模型剩下几秒全部说完？

所以 Claude Code 的思路是：

> 一个完整 Tool Call 一旦从 Streaming 中解析出来，如果当前并发条件允许，就立即开始执行。

这就是：

~~~text
Streaming Tool Execution
~~~

翻成人话：

> 模型一边说，工具一边干。

---

# 3. StreamingToolExecutor 是什么

它是一个专门管理“流式阶段 Tool 执行”的对象。

当前源码：

~~~text
src/services/tools/StreamingToolExecutor.ts
~~~

它不是 Tool 本身。

它更像：

> Tool 调度器。

负责：

- 新 Tool 到达时登记；
- 判断现在能不能开始；
- 允许并发的 Tool 尽快启动；
- 需要独占的 Tool 等前面的任务结束；
- 收集 Progress；
- 缓存 Result；
- 按合适顺序把结果 yield 回 Runtime；
- 中断或 Fallback 时生成错误结果并清理。

---

# 4. 一次流式执行怎么发生

模型 Streaming：

~~~text
t=0s
开始输出文字

t=1s
完整 tool_use A 出现
Read A.ts

t=2s
完整 tool_use B 出现
Read B.ts

t=3s
完整 tool_use C 出现
Grep login

t=5s
模型这一轮输出结束
~~~

如果这些 Tool 都允许并发：

~~~text
t=1s Read A 开始
t=2s Read B 开始
t=3s Grep 开始
~~~

那么到 t=5s 模型结束时：

> 前面的 Tool 很可能已经完成或接近完成。

这就把：

~~~text
模型生成时间
+
工具执行时间
~~~

变成部分重叠。

---

# 5. 为什么不能所有 Tool 都这样跑

现在换一个场景。

模型连续产生：

~~~text
Edit config.ts：修改数据库地址

Edit config.ts：修改缓存地址
~~~

如果两个 Edit 同时跑：

~~~text
Edit A 读取旧文件 V1
Edit B 也读取旧文件 V1

Edit A 写出 V2
Edit B 根据 V1 写出 V3

结果：
V2 的修改可能被 V3 覆盖
~~~

这就是并发冲突。

所以：

> “尽快执行”必须建立在“不互相破坏”的前提上。

---

# 6. concurrent-safe 到底是什么意思

现在再引入专业词。

**Concurrency Safe（并发安全）**：

> 某个 Tool 在和其他并发安全 Tool 同时执行时，不会因为共享状态冲突而产生错误结果。

最容易理解的例子：

~~~text
Read A.ts
Read B.ts
~~~

都只是读取。

通常彼此不改变文件。

所以可以重叠执行。

但：

~~~text
Write config.ts
Edit config.ts
~~~

可能共同修改状态。

通常不应随便并发。

---

# 7. 当前源码并不是简单写“Read=true，Write=false”

这一点要比小林文章的简化模型更准确。

小林用：

~~~text
只读 Tool 可以并发
修改 Tool 需要串行
~~~

来建立直觉，这非常好理解。

但当前真实源码真正调用的是：

~~~text
toolDefinition.isConcurrencySafe(parsedInput.data)
~~~

也就是说：

> 并发安全是 Tool 根据具体输入给出的判断。

所以准确关系是：

~~~text
isReadOnly
和
isConcurrencySafe
经常相关

但不是完全同一个概念
~~~

为什么？

因为一个 Tool 可能：

- 是只读的，但依赖某个共享外部资源；
- 不完全只读，却能保证不同输入彼此隔离；
- 同一个 Tool 在不同参数下并发安全性不同。

所以 Runtime 最终看：

> 这个具体 Tool Call 是否声明自己 concurrency-safe。

---

# 8. StreamingToolExecutor 怎么决定现在能不能开跑

当前核心逻辑可以简化成：

~~~text
如果当前没有任何 Tool 正在执行
→ 可以启动

如果已经有 Tool 执行：
  当前新 Tool concurrency-safe
  并且
  正在执行的所有 Tool 也都是 concurrency-safe
→ 可以一起执行

否则
→ 等
~~~

也就是：

~~~text
safe + safe
可以重叠

unsafe
必须独占
~~~

---

# 9. 为什么“不安全 Tool”必须独占

源码注释的概念很明确：

> Non-concurrent tools must execute alone.

意思：

~~~text
一个 isConcurrencySafe=false 的 Tool 执行时
不应该和其他 Tool 同时运行
~~~

这和普通线程锁思想类似。

先不用学锁。

你只需要理解：

> Runtime 给不安全动作一段独占时间，避免共享状态被其他动作同时改变。

---

# 10. fail-closed 是什么

现在引入一个非常重要的安全思想。

假设 Runtime 无法确定某 Tool 是否并发安全。

有两个选择：

## 选择 A

~~~text
不知道
→ 当作安全
→ 并发
~~~

风险：

> 如果它其实会修改共享状态，就可能造成数据损坏。

## 选择 B

~~~text
不知道
→ 当作不安全
→ 串行
~~~

代价：

> 可能慢一点。

但不会因为判断缺失就冒险。

这叫：

> Fail-Closed。

翻成人话：

> 判断不清时，默认走更保守、更安全的路径。

---

# 11. 当前源码在哪里体现 Fail-Closed

StreamingToolExecutor 里：

~~~text
先 parse Tool Input
~~~

如果输入解析失败：

~~~text
isConcurrencySafe = false
~~~

如果调用：

~~~text
toolDefinition.isConcurrencySafe(...)
~~~

本身抛异常：

~~~text
catch
↓
return false
~~~

也就是：

> 判断并发安全这一步自己出问题，也按“不安全”处理。

另外一些通用 Tool 定义的默认行为也是：

~~~text
isConcurrencySafe = false
~~~

MCP Tool 如果没有提供可用的只读提示：

~~~text
readOnlyHint ?? false
~~~

同样倾向保守。

这就是一个很典型的生产思想：

> 性能优化不能建立在“猜它应该安全”上。

---

# 12. addTool() 到底发生什么

模型流中出现：

~~~text
tool_use A
~~~

Runtime 调：

~~~text
streamingToolExecutor.addTool(...)
~~~

Executor 大致做：

~~~text
找到 Tool 定义
↓
解析 input
↓
计算 isConcurrencySafe
↓
加入 tools queue
↓
立即 processQueue()
~~~

如果现在满足条件：

~~~text
开始 executeTool()
~~~

如果不满足：

~~~text
保持 queued
等待前面 Tool 完成
~~~

所以 Queue 可以理解成：

> 还没轮到执行的 Tool Call 队列。

---

# 13. 为什么结果不能“谁先跑完谁就乱序塞回去”

假设模型按顺序提出：

~~~text
A
B
C
~~~

B 比 A 快。

如果 Runtime 随便：

~~~text
B result
A result
C result
~~~

可能让 UI、消息顺序、某些依赖关系变复杂。

所以 StreamingToolExecutor：

> 可以让执行重叠，但结果输出仍然有顺序控制。

源码注释明确：

> Results are buffered and emitted in the order tools were received.

buffered 可以理解成：

> 结果先暂存，不一定一完成就无条件插进消息链。

这体现一个很好的并发原则：

> 执行可以并行，提交顺序仍然可以受控。

---

# 14. Progress 为什么又可以尽早 yield

长 Tool 可能持续产生：

~~~text
正在搜索……
读取 20%
读取 60%
命令仍在运行……
~~~

这些 Progress 是用户体验信息。

它们不一定要等最终 Result 才展示。

所以 Executor 对：

~~~text
progress message
~~~

会放入独立 pendingProgress，并尽快向外 yield。

于是：

~~~text
最终业务 Result
需要严格处理

Progress
可以更实时
~~~

这也是“状态”和“UI 临时事件”要区分的原因。

---

# 15. 一个 Tool 失败，其他并发 Tool 怎么办

这里当前源码比“所有错误都取消所有兄弟 Tool”更细。

例如某个 Read 失败：

~~~text
Read A
File not found
~~~

其他：

~~~text
Read B
Grep C
~~~

仍然可能有价值。

所以一个普通 Read 错误不一定要把所有兄弟任务都取消。

但 Bash 更特殊。

例如模型并发或批次执行：

~~~text
mkdir build
某个后续 Bash 操作依赖 build
~~~

如果关键 Bash 错误：

> 后面的相关命令继续执行可能没有意义。

当前 StreamingToolExecutor 对 Bash error 有兄弟取消逻辑：

~~~text
hasErrored = true
↓
siblingAbortController.abort("sibling_error")
~~~

其他兄弟 Tool 会获得对应 synthetic error。

这说明：

> “并发失败怎么传播”也必须按 Tool 语义设计，不能一刀切。

---

# 16. sibling 是什么

sibling 就是：

> 兄弟。

这里指：

> 同一个模型响应里，被同一个 Executor 管理的一批 Tool Call。

所以：

~~~text
sibling error
~~~

就是：

> 同批另一个 Tool 出错导致当前 Tool 被取消。

---

# 17. AbortController 在并发里为什么是分层的

Executor 有：

~~~text
主 Runtime AbortController
↓
siblingAbortController
↓
per-tool AbortController
~~~

不用背名字。

理解关系：

## 顶层停止

~~~text
用户 Ctrl+C
↓
整个 Runtime 都应该停
~~~

## 同批兄弟错误

~~~text
某个 Bash 出严重错误
↓
取消相关兄弟 Tool
~~~

## 单 Tool 控制

~~~text
只停止某一个 Tool
~~~

这就是分层 Cancellation。

Cancellation 可以翻成：

> 取消正在进行的异步任务。

---

# 18. Fallback 时为什么必须 discard 整个 Executor

上一章已经提到。

模型 A Streaming 时：

~~~text
Tool A 已经启动
~~~

突然切 Model B 重试。

旧 Tool A 即使最后完成，也已经属于：

> 失败的旧模型轨迹。

所以：

~~~text
streamingToolExecutor.discard()
~~~

会：

- 标记旧执行器作废；
- 阻止排队 Tool 再启动；
- 取消相关执行；
- 避免旧 Result 混进新模型响应。

这本质还是：

> 并发提高性能以后，Runtime 必须额外承担“哪些异步结果现在还有效”的管理责任。

---

# 19. 为什么并发优化会显著增加 Runtime 复杂度

串行世界很简单：

~~~text
做 A
等 A
做 B
等 B
~~~

任何时候只有一件事。

并发以后需要回答：

~~~text
谁正在跑？
谁在排队？
谁可以和谁一起跑？
谁先结束？
结果何时提交？
一个失败要不要取消其他人？
用户中断怎么传播？
Fallback 后旧任务怎么办？
~~~

所以：

> 并发不是“加一个 Promise.all()”就结束。

真正复杂的是状态管理和失败传播。

---

# 20. 为什么不用无脑 Promise.all()

最简单并发代码：

~~~ts
await Promise.all(toolUses.map(runTool))
~~~

问题：

1. 不区分 Tool 是否安全并发；
2. 无法在模型 Streaming 期间提前启动；
3. 中断传播粗糙；
4. 失败后兄弟 Tool 行为难控制；
5. Progress 不容易按需要实时输出；
6. Result 顺序处理更粗糙；
7. Fallback 时旧任务清理麻烦。

StreamingToolExecutor 本质是：

> 为 Agent Tool Calling 专门写的并发调度器。

---

# 21. 一个具体耗时对比

假设：

~~~text
LLM Streaming = 6s

Read A = 3s
Read B = 3s
Grep = 2s
~~~

## 完全串行

~~~text
6 + 3 + 3 + 2
= 14s
~~~

## 模型结束后 Promise.all 三个只读 Tool

~~~text
6 + max(3,3,2)
= 9s
~~~

## Streaming Tool Execution

如果：

~~~text
Read A 在第 2 秒出现
Read B 在第 3 秒出现
Grep 在第 4 秒出现
~~~

则：

~~~text
A: 2s → 5s
B: 3s → 6s
C: 4s → 6s
模型: 0s → 6s
~~~

可能在模型结束附近 Tool 就已经全部完成。

总时间接近：

~~~text
6s + 少量调度开销
~~~

这就是“把等待时间重叠起来”。

# 22. 当前实现和小林文章怎么合并理解

小林的核心教学结论：

~~~text
模型还在吐字
↓
完整 Tool Call 一出来就尽早执行

只读 Tool 可以并发
写 Tool 要谨慎串行
~~~

这个直觉保留。

当前源码补充三点：

## 22.1 真正判断接口是 isConcurrencySafe(input)

不是单纯看“Tool 名是不是 Read”。

## 22.2 判断失败时默认 false

即 Fail-Closed。

## 22.3 Executor 还处理 Abort、Sibling Error、Progress、Fallback、Result Ordering

所以生产实现比：

~~~text
流式 + Promise.all
~~~

复杂很多。

---

# 23. 这套思想怎么迁移到自己的 Agent

如果以后你做 Tool Runtime，可以先设计：

## 23.1 每个 Tool 声明并发属性

至少有：

~~~text
isConcurrencySafe(input)
~~~

不要让 Runtime 猜。

## 23.2 默认不安全

没有声明：

~~~text
→ false
~~~

## 23.3 并发安全 Tool 可重叠

提高性能。

## 23.4 状态修改 Tool 独占

避免共享状态冲突。

## 23.5 并发结果与 Progress 分开

Progress 可以实时。

正式 Result 需要保证协议和顺序。

## 23.6 Cancellation 分层

支持：

~~~text
用户取消整个 Turn
某个批次失败
单 Tool 取消
~~~

# 25. 本章最终心智模型

先记性能目标：

~~~text
模型 Streaming 时间
和
Tool 执行时间

尽量重叠
~~~

再记安全边界：

~~~text
只有明确 concurrency-safe
才允许和其他 safe Tool 一起跑

判断不清
→ 当作不安全
→ 独占执行
~~~

最后记生产复杂度：

~~~text
并发
→ 更快

但同时带来：
状态
顺序
错误传播
取消
Fallback 清理
结果有效性
~~~

所以 Claude Code 不是简单“把 Tool 并行化”。

而是：

> **在能够证明安全的范围里尽量提前执行，并用专门的 Executor 管住并发带来的状态和失败复杂度。**

下一章不再新增新的 Runtime Case，而是把一个贯穿所有 Loop 的问题讲清楚：

> Agent 每轮都把 Tool Result 加回 messages，Context 越滚越大。小林文章讲“413 后 Compact”，但当前源码为什么已经演化成多层 Context 防线？
